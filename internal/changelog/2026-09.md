# Changelog — September 2026

## A resumed sandbox no longer reads a recycled pid as a warm daemon - 2026-09-25

- Session 238 was stopped overnight and resumed at 08:20. Every prompt after that failed as "Turn stalled" — three of them — while `prewarmEntityDaemon` logged `already warm` twenty times over the next 45 minutes. No memory pressure: 2.2 of 16 GiB used, swap untouched, load 0.05, no OOM in dmesg.
- The cause is that all of the daemon's state is marker files under `/tmp`, which ride out a Vercel stop, while the VM itself reboots and pid allocation restarts from 1. `buildDaemonAliveCheckCmd` proved liveness with `kill -0 "$(cat <pidfile>)"`, and the resume had handed the dead daemon's pid to one of the services it spawned — pid 1172, inside the 974–1189 range taken by vite, the Convex backend and the executor. Every prewarm short-circuited on a daemon that did not exist, so nothing ever claimed the staged turn and `turns.finalizeExpired` posted the stall alert.
- `DAEMON_PID_LIVE_FN` (`_sandbox_runtime/daemonPaths.ts`) replaces the bare `kill -0` everywhere it gated a daemon: the alive-check, `buildKillEntityDaemonCmd`'s `reap`, `waitForRunnerReady`'s incumbent probe and the watchdog's `CALLBACK_LIVENESS_COMMAND`. It reads `/proc/<pid>/cmdline` and requires the argv to name `run-design.mjs`, which both pidfiles satisfy and a recycled pid never can. An unreadable procfs degrades to the old `kill -0` verdict rather than guessing.
- Same bug, opposite direction, on the callback side: `claimDaemonPidfileBoot` used `pidAlive`, so a daemon launched onto a resumed sandbox could read the stale pidfile, see a "live rival", and `process.exit(0)` at boot — leaving the entity with zero daemons. It now defaults to `isCallbackRunnerPid`.
- `reap` was the sharp edge: unguarded, a respawn on a resumed sandbox SIGKILLs a whole unrelated process tree, and the pids in range belong to vite and the Convex backend. A boot-id marker was the alternative considered and dropped — it needs new state written by the daemon and a bundle round trip to take effect, whereas argv is already there and is authoritative.
- Tests: `daemonPidReuseContract.test.ts` runs the generated snippet against real processes (a live non-runner must read `cold`, a live runner must not); `killEntityDaemonTreeContract.test.ts` gains a bystander case that must survive a reap; the pidfile-ownership and spawn-lock contracts now pin identity rather than liveness.

## Chat transcripts ship without the step detail nobody is looking at - 2026-09-24

- Switching into a long session was still slow after the earlier chat-switch work, and the remaining cost was the `activityLog` blobs themselves. Measured on a real transcript: 218 KB of activity across 212 steps, of which the per-step `output` (80 KB), `edits` (13 KB) and `contentPreview` fields are 43% — and none of it is on screen until a reader opens a disclosure.
- `messages.listByParent` now runs each payload through `trimActivityLogForTranscript` (`_messages/activityLog.ts`), which parses the steps with Zod, drops those three fields, and marks each stripped step `hasHiddenDetail`. Text-only turns and legacy plain-text logs are returned by identity, so they cost no extra parse.
- Two fields deliberately stay. A `subtask` step's `output` is the sub-agent's final report, which `deriveSubagents` renders in the Agents roster outside any fold; and `detail` on a `reasoning` step is the thinking prose, which `ActivityReasoningBlock` renders inline. Trimming either would have been a visible regression, not a saving — which is why this is 43% and not the 78% a first read of the byte histogram suggests.
- New `messages.activityLogById` serves the untrimmed payload for one message. `ActivityTasks` fires `onRequestFullDetail` when the "Worked for N" fold, an action group, or a row's disclosure opens, and `ActivityLogDisplay` swaps the full log in. It takes a plain string id and normalises server-side, because chat renders optimistic rows under client-minted ids. Deliberately the uncached `useQuery`, so the subscription dies with the chat rather than retaining the bytes this change exists to avoid.
- No new query argument, so the `useSessionSend` / `useSessionAnnotationSend` optimistic inserts are untouched — they write an empty `activityLog` and were already in the trimmed shape.

## An agent can hand over its own preview link - 2026-09-24

- carepulse-ts session 82 built a training demo, was asked "give me the link then?", and answered that no public link existed — offering to merge the PR instead. Its own sandbox was serving the demo the whole time; the agent simply had no way to name it, and on the next ask invented `staging.carepulse.co.uk/demo/referral-portal`.
- New eva MCP tool `get_preview_url`. Called with no arguments it answers for the chat the sandbox token already names, so an agent never has to find its own id; `path` points the link at a route it just built. It returns the live `previewUrl`, the permanent `evaUrl` of that chat's Preview tab, `port`, `ready`, and `sandboxStatus` — a stopped VM comes back as `previewUrl: null` plus "call start_sandbox", never as a guess.
- The URL is grant-stripped before it leaves, the same rule the web app's open-in-new-tab follows: `__eva_grant` is a five-minute bearer token and a chat message is persistent. The opener is bounced through Eva sign-in and back, so the link is for the user and their team, not a public address.
- `getPreviewUrl`'s body is now `buildPreviewUrl`, with the access check lifted to its callers: the public action keeps identity plus the sandbox↔repo binding, and the MCP path resolves the chat as its user first, so the sandbox id it passes came off a document that user can read. `resolveChatTargetForUser` carries `sandboxId`, `sandboxStatus` and `devPort` (entity before repo default) so one lookup answers everything the tool needs.
- Session, quick-task and project chat prompts gained a Preview link section next to the dev-server one — call the tool, paste what it says, never claim no link exists and never guess a staging address for unmerged work. Manager Ave's delegate list names it too.

## Sending from the new-session composer lands on the session again - 2026-09-24

- Hitting send on the landing composer created the session and then left the user sitting on the composer. One cause, introduced by #713 (2026-09-18) when `CodebasesPicker` replaced `ComposerAppSwitcher`: a second navigation was overwriting the first.
- `handleSend` cleared the codebases picker — `codebases.clear()` — between creating the session and navigating. That selection is query-string state owned by nuqs, and nuqs does not write the URL inline: it queues the update and flushes it on a later tick through its TanStack adapter, which navigates to `pathname + search` with the pathname captured when the adapter last rendered. That pathname is the composer's, and the flush landed after `navigate`, replacing the new session's URL with the composer's (`replace: true`, so not even a history entry survived). `ThrottledQueue.push` enqueues unconditionally, with no equality check, so this fired even for users who never opened the picker.
- The clear is gone. Leaving the page already drops `linked` / `group` / `deps` — `navigate({ to })` carries no search — so there was nothing for it to clean up. `clear()` itself stays on `useCodebasesSelection` for the delete-a-saved-group path, which does not navigate.
- #802 (2026-09-22) read the same symptom as a routing bug and wrapped this destination in `toInternalRepoHref`. That was a misdiagnosis: `router.navigate({ to })` passes through the `rewrite.input` in `main.tsx`, so slash-form and `repo--app` destinations already resolved to the same match, and the bug returned untouched. The wrapper is harmless and stays, but `basePath` being a display-form string that ~30 call sites hand-convert is what made the wrong explanation plausible — folding the conversion into a `useRepoNavigate` helper would retire the whole question.
- `newSessionSendContract.test.ts` pins that nothing between `createSession` and `navigate` writes URL state. It asserts on source text, not behaviour — a real regression test needs a DOM env, and `apps/web` has no jsdom or testing-library today. The same shape is worth watching anywhere a nuqs setter runs in a handler that then leaves the page.

## Quick task and project chat queue follow-ups like sessions do - 2026-09-24

- Typing a follow-up while a quick task was running did nothing: the composer was disabled outright. Session chat has always queued in that window, so the three surfaces disagreed on the one thing a chat is for while it is busy.
- The cause was the gate each panel wrote for itself, `!isSandboxActive || isSwitchingAccount`. A quick task's first run owns the sandbox and only marks it `active` on the way out (`markTaskSandboxActive`, 2026-09-23), so for the whole run the chat was read-only. Sessions never hit it because a session's sandbox is active whenever a turn runs.
- All three panels now call one `sandboxComposerState` helper: a running turn always accepts input, because that send is queued rather than handed to the sandbox. It returns the placeholder and the blocked-Enter reason too, so the copy cannot drift apart again. `SANDBOX_CHAT_COPY.firstRunDisabledReason` is gone — there is nothing to refuse.
- Backend had to catch up on both sides of that window. `taskChatQueueConfig` now counts the task's own `activeWorkflowId` as busy, so a drain cannot start a chat turn on top of the run and put two agents in one sandbox. And `clearActiveWorkflow` drains the task chat queue once the last run settles — nothing else did, so a message queued during the first run would have waited forever.

## A quick-task run stops its sandbox again - 2026-09-24

- Reverts "A quick-task run leaves its sandbox up, and writes the PR description at code review" (#820, below). Leaving the sandbox up meant every quick-task run parked a live Vercel VM until the next day's idle sweep reaped it; the run stops (never deletes) its sandbox once more, so the cost is paid only while someone is actually reviewing.
- `markTaskSandboxActive` is `markTaskSandboxStopped` again, writing `reviewTaskSandboxStatus: "closed"` and keeping `sandboxId` so Start Sandbox and follow-up runs resume the same paused filesystem. The stop is back on both exits of the workflow (success path and `catch`) rather than the `finally`.
- The two escape hatches came back with it: `preserveSandboxOnFailure` keeps the sandbox after a failed publish so the evidence survives, and `keepTaskSandboxActiveAfterRun` (derived in `getTaskData` from `reviewTaskSandboxStatus === "active"`) leaves a preview the reviewer already has open alone, so a change-request run does not pull the VM out from under them.
- The diff-derived PR description stays where #820 put it: written once, when the reviewer moves a quick task to `code_review` (`agentTasks.updateStatus`), not at the end of every run. The run-time call is gated back to project tasks, which share one PR and never make that transition.
- Because the run now stops the sandbox, that description call would have found a dead VM. `generatePrDescription` takes `restoreStoppedSandbox`: the quick-task review path resumes the sandbox for the one model call and stops it again in a `finally`, so a failed description cannot leak the VM. The flag is skipped when `reviewTaskSandboxStatus === "active"`, so a preview the reviewer has open is never pulled down.
- `taskSandboxStoppedAfterRun.test.ts` replaces `taskSandboxActiveAfterRun.test.ts` and pins the three stop gates, the project-only run-time description, and the resume/re-stop pairing.
## Scope verdict reaches the pull request, and quick tasks can answer a blocking question - 2026-09-23

- **The warning travels to the PR.** `_github/prScopeSection.ts` writes a "Changes nobody asked for" block into the PR body — plain-English rows (`Icon changed (IconAward → IconTrophy) — Awarded panel`), unreported ones first and labelled. `publishScopeSection` (`_github/prScopeCheck.ts`) reads the PR's commits and asks `flaggedForShas` for verdicts recorded against those shas. Until now the verdict only existed in the Eva chat, which is no help to a reviewer on GitHub.
- **Keyed on the commit, not the chat.** New `messages.by_after_sha` index. Two triggers: `setScopeCheck` publishes as soon as a flagged verdict lands and the chat has a PR (a quick task's PR lives on its newest `agentRuns` row, not on the task), and the `pull_request` webhook publishes on `opened`/`reopened` for PRs Eva did not open.
- **Known gap, stated rather than papered over:** a squashed or hand-copied extract mints new shas, so it still shows nothing — which is exactly how the original trophy reached prod (PR #1889). Closing that means matching on file paths, trading exactness for noise. Documented in `docs/scope-check-surfaces.md`.
- `prDescriptionPrompt.ts` and the new section now share `_github/prBodyBlocks.ts` for the marker splice, so rewriting one generated block never disturbs the other; an empty verdict removes its block rather than writing a reassuring heading. Existing `prDescription.test.ts` guarded the refactor; `tests/prScopeSection.test.ts` pins the two-block interleaving.
- **The PR description now flags unrequested visuals too.** Its Review notes lead on visible changes the Intent did not ask for (icon, colour, copy, a control that moved), and skip that bullet entirely when no Intent was supplied rather than guessing. This is the only such check a quick task **run** gets — a run stamps no turn diff, so the scope chip never judges it. Deliberately not a rule in the run prompt: the run summary is capped at 3–5 plain-language bullets, so an exhaustive change list loses that fight, and it would rely on the same agent noticing what it did. The description model reads the whole diff and the task description side by side instead.
- **Blocking questions beyond sessions.** `BLOCKING_QUESTIONS_ENABLED` was `ENTITY_ID_FIELD === "sessionId"`, so an agent on a quick task or project chat asked into the void. All three panels already query `pendingQuestions.getActive` and write answers back, so the gate is now the three chat surfaces — and explicitly **never on a `RUN_ID`**: a run has nobody to answer and the pause suspends the turn watchdog, so it would hang until someone stopped the sandbox. `callback-src/tests/blockingQuestionsGate.test.ts` pins both halves. Callback bundle rebuilt; running sandboxes pick it up on restart.

## Scope chip names the change in English, and flags what the reply never mentioned - 2026-09-23

- A trophy icon nobody asked for shipped to prod inside a large tabs feature (carepulse-ts task #200 → PR #1889). Two failures, not one: the agent chose a visual it was not asked for, and its reply never said so, so no reviewer could catch it. The chip that exists to catch this reported `…/AwardedPanel.tsx` plus an `@@` header — unreadable to the designer who owns that review.
- **Plain English.** The per-hunk Jev call now also asks a `kind` choice (icon, colour, wording, layout, motion, new element, behaviour, content, internal). It rides in the existing call, so classification costs nothing. `_scopeCheck/describe.ts` turns that into a headline: a pure extractor diffs the hunk's `+`/`-` sides for icon components, colour literals (hex, Mantine shade, CSS var, Tailwind class) and quoted copy, giving `Icon changed (IconAward → IconTrophy)`, and `humaniseSurface` turns the path into a screen name (`page.tsx` borrows its folder, `[id]` is skipped, `(group)` keeps its name). The file path moves to the row's `title`.
- **The mention cross-check.** Each flagged hunk gets one more Jev boolean against the assistant's reply: did the reply tell the user about this change? `getTurnContext` now returns the reply for it. The chip leads with `1 change not mentioned` and the row says `· not mentioned in the reply`, because a change the turn owned up to is already in front of the reader whether or not it was asked for. Absent means the question went unanswered, never "the reply stayed silent".
- Cost is bounded by the flagged set, not the diff: mention calls only run for hunks the chip will show (capped at 20, usually 0–3), batched six at a time like the scope pass. Every new field on `scopeCheckHunkValidator` is optional, so rows judged before this keep rendering from file and header.
- Prompt side, same failure: every chat turn now carries a `VISUAL_CHANGE_INSTRUCTION` block — reuse the existing pattern, else ask before building (blocking `AskUserQuestion` where it exists, `render_ui` reply buttons everywhere else), never stall when nobody can answer, then report every visible change with invented ones labelled. Deliberately scoped to *visible* choices: "ask whenever unsure" stalls turns and trains users to wave questions through. The Designer role preset demands invented choices first.

## Switching into a long chat paints the latest turn first - 2026-09-22

- Opening a heavy session used to commit the whole transcript in one blocking render. Measured on a seeded 84-message / ~1.9 MB-of-activity-log session (local dev build): the latest turn appeared 1.71–1.77 s after the click, inside a single 0.97–1.15 s task that froze the tab.
- `ChatBody` now splits the transcript. The latest turn renders urgently; everything above it — which `ChatLastTurn` already keeps out of the viewport by padding the last turn to `100cqh` — renders one pass later behind `useDeferredValue(displayMessages.length > 0, false)`, at transition priority that React time-slices. Same session: latest turn at 0.65–0.78 s, longest blocking task 0.32–0.39 s, total long-task time down from 1.54–1.86 s to 0.79–1.02 s.
- Deferring "the transcript has rows" rather than component mount is deliberate: a chat whose messages land after mount would otherwise spend its deferred pass on the loading skeleton and then commit the entire backlog in the first render that has data. That version measured no faster than before.
- Backlog rows pass `animateIn={false}` to `ChatMessage`, so 80 turns no longer replay an enter animation for messages that did not arrive. New and latest turns animate as before.
- `useTurnCheckpointActions` builds its two Radix dialog roots on first open instead of per assistant turn, and `ChatJumpRail` mounts with the backlog, since it binds its IntersectionObserver to `[data-message-id]` once and would otherwise observe nothing.
- `content-visibility: auto` on backlog rows was tried and reverted: no intrinsic-size estimate fits a chat turn, and scrolling up grew the scroll height from 19k to 36k px.
- Not addressed: the transcript payload itself. On the heaviest production session (52 messages, 2.2 MB of `activityLog`), 78% of those bytes are the per-step `output`, `detail` and `edits` fields, which only render inside an expanded disclosure. Trimming them from `messages.listByParent` and fetching them on demand is the next lever, and the one that matters most over a real network.

## Seeded snapshots wait for the Convex push before importing data - 2026-09-21

- A seeded build imported a whole staging backup into cost-model-ts and then lost all of it to `Could not complete import because schema changed`. The seed run's Convex gate only waited for the local backend to answer on `:3210`, so `npx convex import` started while the `convex dev` daemon was still applying `schema.ts` and backfilling its indexes; the daemon's push finished 8s in, mid-import, and `npx convex import` aborts the entire restore on a schema change rather than the table it was on.
- `launchSeedRun` (`convex/snapshotActions.ts`) now follows the fatal health gate with a second, non-fatal wait for `Convex functions ready` in `/tmp/bg-<i>.log`, bounded by `CONVEX_FUNCTIONS_READY_ATTEMPTS` (60 × 5s) and ended early by a dead supervisor pid. Repos whose first push succeeds break out in seconds (8s observed on cost-model-ts, ~60s on CarePulse).

Repos currently carry this as a hand-rolled `grep -q "Convex functions ready"` startup command (CarePulse web/eprocurement, cost-model-ts); those are now redundant and can be dropped.
- `seedRunConvexGateContract.test.ts` pins the wait's position before the seed commands and that it stays bounded, alongside the existing rules that keep it non-fatal.

## Scope check: Jev flags turn changes the prompt did not ask for - 2026-09-22

- Every assistant chat turn that changed code is judged out of band by TypeSafe Jev: was each change asked for? The verdict lands on the message as `messages.scopeCheck`, so the signal is per turn and per message rather than per task, and can inform how thorough a review needs to be. Session, quick-task and project chat all carry it, `/loop` continuations included; quick-task runs do not, because they deliberately never checkpoint.
- Judged per diff hunk, not per PR: the motivating case was an icon swap inside a file the agent was legitimately editing, which a whole-diff question drowns. Each hunk gets two booleans — "requested" and "necessary to make a requested change work" — and is flagged when both lean negative (< 0.5), so collateral imports and call-site updates stay in scope. One whole-diff question over the same filtered hunks supplies the headline probability.
- The diff comes from GitHub's compare endpoint (`fetchCompareDiff`, already used for "Diff this turn"); a sha GitHub has not received yet is retried twice at 30 s. Lockfiles, binaries and generated output (`*.generated.*`, `_generated/`, `*.min.js`, `dist/`) are skipped before anything reaches Jev. Hunks are capped at 60 per turn and 3,000 characters each, the headline diff at 30,000 characters — the gateway answers a 41k state but 503s on 77k, well below Jev's 200k schema cap. Every failure path leaves the field absent.
- Chat shows an always-visible chip under the reply: "In scope" (muted, < 35%), "Check scope" (warning), or "N unrequested changes" (destructive, ≥ 65% or any named hunk), with a hover card listing each flagged file and hunk that opens the turn diff on click. Hidden in simple view like other diff surfaces.
- Extending beyond sessions needed the callback's checkpoint gate to become an allow-list of `sessionId`/`taskId`/`projectId` (`callback-src/runtime/turnCheckpoint.ts`) and the task/project completion chains to stop dropping the shas. `docs/scope-check-surfaces.md` records the order that matters — persistence first, gate second — and why: stamping shas a surface cannot persist once hung turns in prod.
- Live calibration on a synthetic Copy-link feature: the stray icon-swap hunk scored 9% requested, a needed toast import 85%, a new test file 74%, an unrelated variable rename 5%; whole-diff read 81% with the swap and 9% without.

## Generative UI in chat: agents can render interactive panels with `render_ui` - 2026-09-21

- New MCP tool `render_ui`, available on every session / quick task / project sandbox token. The agent hands Eva a `prompt` (layout only) plus up to 24 content `blocks` — heading, text, metric, badge, callout, progress, checklist, table, keyValue, code, image, button — and a panel appears inline in the chat under that turn. Every word on screen comes from the agent; nothing is model-written at render time.
- Layout is composed by json-render's experimental Jev path (`experimental_composeSpec` + `experimental_createEvaluator` against `typesafe-ai/jev` on AI Gateway), so a panel is a handful of typed choice decisions rather than a generated JSON blob, and it settles in about a second. Composition is constrained to the shared catalog in `@eva/shared/generativeUi` — 16 components and two actions (`reply`, `open_url`) — so a spec can never name anything the chat has not registered a component for.

## Daemon no longer exits on a lease verdict for a turn it finished itself - 2026-09-21

- Root cause from prod (eva session 225, 21 Sep 2026, "Turn stalled … process_dead", VM idle with 9.4 GB free): the Claude daemon posted `completeSyntheticTurn` for a finished synthetic turn at 11:21:13.169Z; a streaming heartbeat still carried that turn's lease and was processed 58ms later, after the server had closed the turn, so it came back `terminal: closed`. `noteHeartbeatResponse` treated any terminal verdict as "a rival owns this turn", `enforceTurnLease` armed its 500ms exit, and in that window the pump minted the next synthetic turn (11:21:13.401Z). The process exited at 11:21:13.813Z with exit code 0, leaving the new turn's 2-minute lease with nobody heartbeating it; `turns.reconcile` finalised it as stalled at +2.5 min. The same window exists for real turns between the completion mutation and `finishClaimedTurn` (media upload runs in between) whenever the workflow closes the turn quickly.
- Fix, daemon side (`callback-src`): `noteHeartbeatResponse(response, sentUnder)` now only fences when the verdict is for the lease this process still holds (`isSameTurnLease`); a reply for a released or older lease is logged as `stale turn lease verdict ignored` and dropped. Both heartbeat senders in `http/convexClient.ts` capture the lease once before building the request and pass that identity back. New `releaseTurnLeaseForCompletion()` is called after the completion payload has taken the lease and before the closing mutation is sent, in `deliverCompletionWithMedia`, `postClaimedTurnFailureCompletion`, `finalizeSyntheticTurn`, `failSyntheticTurn` and the pump-failure path, so no heartbeat is emitted under a lease the server is about to close. Server-side lease logic is unchanged: `closed` is the correct answer, the client just stopped misreading it. Bundle regenerated.
- Tests: `callback-src/tests/turnLease.test.ts` covers stale verdicts (released lease, next turn owned, older generation, lease-less legacy owner) and `isSameTurnLease`; `tests/turnLifecycleContract.test.ts` pins release-before-send in every completion path and the captured-identity wiring in both heartbeat senders, including the rebuilt bundle.
- Not addressed: `LEASE_EXIT_GRACE_MS` still exits even if a new turn is minted in the 500ms window; with stale verdicts no longer fencing, that latch only fires for real takeovers, cancels and timeouts, where exiting is right.

## Multi-repo sessions (codebase groups) - 2026-09-03

A session can now span several connected GitHub repos instead of one. Work that crosses a frontend and its backend, or an app and a shared library, no longer needs two sessions, two agents and hand-copied context between them.

- **Pick extra codebases in the composer.** The new-session composer has a codebases picker: the current repo is the primary, and you add linked repos as chips. The selection lives in the URL, so it survives a reload and can be shared. Repos are deduped by `owner/name`, and two repos with the same GitHub `name` are refused — they would collide on one workspace folder.
- **Saved codebase groups.** Save a selection as a named group and reuse it. Groups are visible to the primary repo's team when it has one, otherwise to the creator. Rename, edit membership, or delete from the picker.
- **One sandbox, all repos.** The primary keeps its home at `/tmp/repo`; every repo appears under `/tmp/workspace/<name>` (the primary as a symlink). The agent is told about each repo's path, branch and base, and commits per repo. Each linked repo gets its own `.env.eva` with its own Eva env vars, rather than merging conflicting keys into one sandbox-wide file.
- **The first turn waits for the clones.** Linked repos are cloned and installed before the session's first turn is claimed, with per-repo progress in the startup timeline. One repo failing to clone posts an alert naming it and does not block the others or wedge the session.
- **Cross-org repos work.** The in-sandbox git credential helper now sends the repository it is authenticating for, and Eva mints a token for that repo's own GitHub App installation — but only from the allow-list recorded for that sandbox, so a sandbox can never mint for an installation its session does not use.
- **Per-repo PRs and archiving.** Each linked repo gets its own branch and its own draft PR, cross-linked to its siblings; the session archives only when every PR it opened is merged or closed. Session header, sidebar, files panel and the changed-files card all show which repo a thing belongs to, and a session shows up under each of its linked repos with a "via `<primary>`" hint.
- **Diff and restore cover every repo.** Turn checkpoints record HEAD per repo, and "restore to before this turn" is all-or-nothing across them, so repos never end up on mismatched turns.
- **Group snapshots keep starts fast.** Saving a group builds a seeded snapshot containing the primary plus every linked clone with dependencies installed, so fresh sandboxes only fetch instead of cloning and installing. It is fingerprinted on membership and rebuilt when that changes.
- **MCP.** `create_session` takes `linkedRepos` or a `group` name, `list_repos` lists saved groups, and `get_agent_state` / `list_entities` report each session's linked repos with their PRs.
- Docs: `docs/multi-repo-sessions.md`.

## Preview iframes no longer carry two same-name cookies (wrong-account sessions) - 2026-09-10

## Sandbox validate/background-launch paths recover from OOM-wedged VMs (exit 137, hung execs) - 2026-09-01

- Root cause (prod, silver-strategic-buzzard, 2026-09-01 ~16:45 UTC): an OOM-wedged VM still reports `running` to Vercel, so `ensureSandboxRunning` no-ops on `start()` and its `echo 1` probe dies with exit 137; every path then cascaded — `runBackgroundCommands` burned a 25s client timeout (or a `Status code 400 is not ok`) per command, and its un-try/catch'd pid-check/cleanup execs threw the whole action Uncaught into scheduled callers and the preview heal.
- New typed `SandboxExecTimeoutError` (same message wording, so setup-retry matchers are unchanged) plus `isSandboxUnresponsiveError` (exit 137 on cheap commands / client-side exec timeouts). Deliberately not `sandbox-gone`: the record exists, so the reaction is restart-or-unhealthy, never minting a replacement VM.
- New `restartUnresponsiveSandbox` helper: stop (snapshots the disk) + resume, which also re-provisions swap. Gated on a fresh `running` state read so it can never resurrect a sandbox the user just stopped.
- `validateSandbox` attempts that stop+resume once on an unresponsive signal before reporting `healthy: false` (callers already recreate on unhealthy); other failures keep the old behavior.
- `runBackgroundCommands` wraps the whole per-command body in one try/catch and classifies failures: per-command errors on a live VM continue as before; a wedged VM gets one stop+resume then a retry (never on the `onlyRestartDead` preview-heal path, which must not restart a VM mid-turn); a confirmed-dead or not-running VM aborts the remaining launches with the skip recorded in `errors` instead of cascading timeouts or throwing Uncaught. A provider 400 alone proves nothing and is confirmed with an `echo 1` probe, run only after the state check says `running` so it cannot lazily resume a stopped VM.
