## Spinners, text shimmer and border beams cost less to animate - 2026-09-05

- Method: a CDP tracing harness against the sandbox's shared Chrome — a fresh tab per run, `Tracing.start` over the timeline/cc/viz categories, busy time merged per thread (renderer main, cc Compositor, viz compositor), plus paint/style/raster counts. The sandbox has no GPU (`gpu_compositing: disabled_software`), so compositor and filter work is CPU time on the viz thread and reads high against a real GPU; main-thread numbers transfer as-is. Every before/after pair was traced in interleaved rounds, medians of three, with the "after" CSS extracted verbatim from the shipped `globals.css`. Visual parity was checked by pausing every animation (WAAPI and SMIL) at the same time offset and diffing screenshots with ffmpeg SSIM. Figures are per second of animation.
- `Spinner` (`packages/ui/src/ui/spinner.tsx`): SMIL `<animate>` → WAAPI `polygon.animate` from a module-stable ref callback with cleanup (the `LoadingState` pattern). SMIL ticked each polygon's attribute on its own, forcing ~9 style recalcs a frame. Eight spinners: style recalcs 420 → 49/s (−88%), main thread 48.7 → 30.8 ms/s (−37%), renderer+compositor CPU 102 → 88 ms/s (−14%). Frames byte-identical at the same offset. Still self-contained — no stylesheet keyframes.
- `Shimmer` (`packages/ui/src/ai-elements/shimmer.tsx`; "Working for", "Thinking...", streaming plan titles): the `background-clip: text` + `background-position` sweep repainted the glyphs every frame. It is now a copy of the text in the highlight colour, masked to the same soft band; the band translates one way and the copy inside it translates back by the same amount, so only the mask moves and both animations are compositor transforms. Four instances: main thread 32.6 → 1.9 ms/s (−94%), paints 240 → 0/s, total CPU 89 → 69 ms/s (−23%); the mask adds one render pass per instance (viz +12 ms/s in software). Band travel (−0.25w → 1.25w), width and duration match the old sweep; SSIM 0.9998 against the old frame. `@keyframes shimmer-sweep` removed; `shimmer-overlay` / `shimmer-band` / `shimmer-copy` and `@keyframes shimmer-band` added to `globals.css`.
- `BorderBeam` (`globals.css`): each spinning gradient square is sized to its clip's diagonal — `container-type: size` on the clip, `calc(hypot(100cqw, 100cqh) + 12px)` on the pseudo (the +12px covers `.beam-inset`'s padding) — instead of 150% of the host width, and centred with a static `translate` that composes with the `rotate` animation on the compositor. On the composer (762×114 clip) each cached texture shrinks from 1143² to 783² px, −53% of texture memory and one-off raster per layer (×4 at 2× DPR). Ring composite 173 → 164 ms/s (−6%); glow and card beams unchanged within run-to-run noise (±7%). The halo spins `linear` instead of `steps(90)`: both traced the same cost because the blur re-runs whenever the ring damages the frame, so the 30Hz cap only made the glow stutter. Ring and halo rules merged (identical clip and square). Rejected on measurement: replacing the blur with three stacked hard-edged bands (+11% compositor time in software).
- Realistic chat mix (composer beam with glow, send-button spinner, one shimmer, three sidebar grids): main thread 64 → 45.5 ms/s (−29%), style recalcs 138 → 46/s (−66%), paints 138 → 93/s (−33%), total 358 → 328 ms/s (−8%; the beam's software composite dominates and is unchanged).
- Also rejected: `will-change: transform` isolation for spinners (paints 93 → 402/s, total +13%). Already compositor-only and left alone: `animate-spin` icons, `LoadingState` grids (WAAPI opacity) and `Skeleton` sweeps (main thread ≤ 1 ms/s each).

No new user bubble; the original user row's `credentialSourceLabel` moves to the new account. `null` means the team credential. Account usability is enforced by the existing `owner-pool` resolution, so only accounts the session owner may use are accepted.
- The failed reply itself no longer renders as markdown body copy reading "Error: …": `ChatMessage` swaps in `TurnErrorNotice` (`lib/components/chat`) for `errorType === "rate_limit"` — a destructive-tinted tone surface with an icon, the title "Claude usage limit reached" and the provider's text underneath, stripped of the harness's `Error: ` stamp (`stripErrorPrefix` in `chatBodyUtils.ts`). - `UsageLimitRecoveryBanner` (sessions `_components`) sits under `PublishRecoveryBanner` and shows while the newest message carries `errorType === "rate_limit"`. It is a recovery card, not a button strip: header "{Name}'s Claude account is out of usage" / "The team Claude account is out of usage" with "Resets in 2h 10m (12pm UTC)" underneath (`parseUsageLimitResetTime`, now exported from `@eva/backend` via the import-free `_taskWorkflow/usageLimitReset.ts` so the web bundle does not pull in `workflowManager`; falls back to the provider's own `resets …` text when unparseable or already past). The banner therefore awaits the existing handoff (`sessions.setProviderAccountId` then `prewarmDaemonNow`) before calling the retry mutation. `useProviderAccountHandoff.switchProviderAccount` now returns that promise instead of firing and forgetting; the three existing callers are unchanged apart from a `void`.
- Tests: `packages/backend/tests/usageLimitRetry.test.ts` pins the stamp to `isUsageLimitError` and the retry to `stageAndStartSessionTurn`/`resultTargetMessage` with no mention notification; `usageLimitBanner.test.ts` covers the reset-fragment extraction. ## Cursor turns no longer stall on resume: SDK agent store moved from JSONL to SQLite - 2026-09-03

- Symptom (prod, sessions 174 and 176, 3 Sep 19:17–19:24 UTC): every grok-4.6 turn after the first failed with `Cursor stalled while starting the model run for 60 seconds` — once, then again on the same-agent retry, then the turn died, ~123s burned per failed turn. The failing phase was `Agent.send()` on a resumed agent inside `runCursorSdkAttempt`.
- Root cause: the store, not Cursor. Eva persisted agents with the SDK's `JsonlLocalAgentStore` at `CURSOR_SDK_STORE_DIR`, which re-reads and JSON-parses the entire file on every `get` and rewrites it whole (tmp + fsync + rename) on every `append`/`create`/`update`, with checkpoint blobs base64-encoded inside `checkpoints.ndjson`. A resumed `send()` hydrates the conversation blob by blob: in an end-to-end reproduction against the real pinned SDK, a resume after a 12-tool-call first turn issued 56 `checkpoints.get` calls before returning the run handle, against a `checkpoints.ndjson` already 793 KB. Blob count and file size both grow with the conversation, so resume was quadratic in conversation length. Session 174 had ~580 tool steps over its first three turns, which extrapolates to thousands of full-file reads of a file in the hundreds of MB. A micro-benchmark of the JSONL store measured ~1.2s per `get`/`append` at 168 MB of events plus 427 MB of checkpoints. The same per-step pattern (2 gets + 2 creates per tool step, each a full read or rewrite) also taxes every step of a long first turn.
- `runCursorSdkAttempt` (`callback-src/providers/cursorSdk.ts`) now opens the SDK's own `SqliteLocalAgentStore` at the same `CURSOR_SDK_STORE_DIR` (`stateRoot`, `workspaceRef: WORK_DIR`), per attempt, disposed in the `finally` beside `agent.close()`. It loads from the pinned SDK's separate `dist/esm/sqlite.js` entry through `resolvePinnedSdkEntry` and a second memoized loader, kept apart from `loadCursorSdk` because that entry exists precisely so the main one does not pull in the sqlite driver. Same reproduction, SQLite store: the resumed `send()` returned in 24ms with every store call at ~0ms. No timeout, retry or `agent_not_found` logic changed.
- Migration: none, deliberately. The SQLite layout is `index.db` plus `agents/agent-<sha256>/store.db`; legacy `*.ndjson` files sitting in the directory are ignored. A session whose agent id was saved before this deploy resumes as `agent_not_found`, and the existing `canReplaceCursorAgent` recovery starts a fresh agent once with the usual "Started a fresh Cursor agent" notice. Reading those legacy files is the slow path being removed, so migrating through it would reintroduce the stall.
- Tests: `tests/providerSdkDependenciesContract.test.ts` pins `SqliteLocalAgentStore` against the pinned `@cursor/sdk` 1.0.28 sqlite bundle, pins the entry path and the `open({ stateRoot: CURSOR_SDK_STORE_DIR })` call in the loader, and asserts that neither the loader nor `convex/_sandbox_runtime/callbackScript.generated.ts` mentions `JsonlLocalAgentStore` — so a stale bundle fails the build. Callback bundle regenerated.
- Operational note: `node:sqlite` prints an `ExperimentalWarning` on stderr under Node 24. It is harmless and does not reach the turn output.

## Session turns no longer hang on "Working…" after a daemon respawn - 2026-09-02

Prod session 166 (sandbox white-advisory-iguana-fez4UA, 21:00 UTC): a prewarm launched the warm Claude daemon, a second prewarm one second later saw "model/tools changed" and killed it, the relaunch reported "runner ready" in 827ms, and then nobody polled `claimPendingTurn` for the whole turn. Three independent defects lined up:

- `AGENT_PROCESS_LIVENESS_COMMAND` (`_sandbox_runtime/lifecycle.ts`) ran `pgrep -f 'claude-code|…'`, but every exec is wrapped in `bash -lc "<cmd>"`, so the pattern matched the wrapper's own cmdline and `verifySandboxLiveness` could never report a dead callback on a running VM. The stall watchdog took `agent_process_running_callback_pid_stale` as confirmed alive, touched the streaming row and reset the staleness clock every cycle, so the turn would only die at the 2h backstop. Each alternative is now bracketed (`[c]laude-code`, `/[.]claude/`), the same trick `KILL_PRIOR_AGENT_PROCESSES_CMD` already used. Pinned by `tests/agentLivenessPgrepSelfMatchContract.test.ts`, which builds a RegExp from the source pattern and checks it rejects `bash -lc <pattern>` while still matching real agent cmdlines.
- `buildKillEntityDaemonCmd` (`_sandbox_runtime/daemonPaths.ts`) sent one SIGTERM to the daemon pid. The daemon boots its `query()` at startup, so its Claude CLI child was orphaned holding the inherited `flock -n -E 217` fd, and the relaunch lost the spawn lock. It now collects descendants with `pgrep -P`, signals the root first (the daemon has no SIGTERM handler, and killing the child first would let it post a bogus "daemon failed" completion), recurses into the children, waits up to 3s per pidfile for the root to exit, then escalates to SIGKILL. On Fable 5 / Opus 5 / 4.8 / 4.7 / Sonnet 5 the API's `thinking.display` default is `omitted` (a silent change from Opus/Sonnet 4.6, where it was `summarized`), so `thinking_delta` events arrived with empty text. `claudeParseLine` already handled `thinking_delta` and `thinking` blocks correctly — it just never received any text, so the `reasoning` step stayed empty and the UI showed a long pause where Cursor shows "Thinking...".
- `buildSdkOptionsFromParts` (callback-src/providers/claudeSdk.ts) now passes `thinking: { type: "adaptive", display: "summarized" }` unless the user turned thinking off. Thinking-off keeps the existing `--settings` `alwaysThinkingEnabled: false` path and sends no `thinking` option — Fable 5 rejects an explicit `{ type: "disabled" }` with a 400. `claudeThinkingDisabled` moved to config.ts so both consumers share one definition.
- Regression pins in `callback-src/tests/canonical.test.ts`: a Claude `thinking_delta` routes to `update_reasoning`; an empty one emits nothing (the pre-fix symptom). Callback bundle regenerated.

## Sandbox validate/background-launch paths recover from OOM-wedged VMs (exit 137, hung execs) - 2026-09-01

- Root cause (prod, silver-strategic-buzzard, 2026-09-01 ~16:45 UTC): an OOM-wedged VM still reports `running` to Vercel, so `ensureSandboxRunning` no-ops on `start()` and its `echo 1` probe dies with exit 137; every path then cascaded — `runBackgroundCommands` burned a 25s client timeout (or a `Status code 400 is not ok`) per command, and its un-try/catch'd pid-check/cleanup execs threw the whole action Uncaught into scheduled callers and the preview heal.
- New typed `SandboxExecTimeoutError` (same message wording, so setup-retry matchers are unchanged) plus `isSandboxUnresponsiveError` (exit 137 on cheap commands / client-side exec timeouts). Deliberately not `sandbox-gone`: the record exists, so the reaction is restart-or-unhealthy, never minting a replacement VM.
- New `restartUnresponsiveSandbox` helper: stop (snapshots the disk) + resume, which also re-provisions swap. Gated on a fresh `running` state read so it can never resurrect a sandbox the user just stopped.
- `validateSandbox` attempts that stop+resume once on an unresponsive signal before reporting `healthy: false` (callers already recreate on unhealthy); other failures keep the old behavior.
- `runBackgroundCommands` wraps the whole per-command body in one try/catch and classifies failures: per-command errors on a live VM continue as before; a wedged VM gets one stop+resume then a retry (never on the `onlyRestartDead` preview-heal path, which must not restart a VM mid-turn); a confirmed-dead or not-running VM aborts the remaining launches with the skip recorded in `errors` instead of cascading timeouts or throwing Uncaught. A provider 400 alone proves nothing and is confirmed with an `echo 1` probe, run only after the state check says `running` so it cannot lazily resume a stopped VM.

## Session sandbox reuse recovers from an unresolved merge index - 2026-09-01

- Reusing a session sandbox died with an uncaught `SandboxCommandFailedError` when a previous agent run left the VM mid-merge: every `git checkout` refused with "needs merge; error: you need to resolve your current index first", reuse could not fall back to a fresh VM (the old one was alive and `fallbackOnPrepareError: false` guards against orphaning it), and `sessionExecuteWorkflow` aborted (prod session n97ex5wm, 2026-09-01).
- `checkoutSessionBranchWithRetry` now detects git's unresolved-index refusals (`isUnresolvedGitIndexError`: "needs merge", "resolve your current index first", "unmerged files", "MERGE_HEAD exists") and runs a one-shot `recoverUnresolvedGitIndex` before retrying: abort any in-progress merge/rebase/cherry-pick/revert (each gated on its `.git` marker), then reset unmerged index entries only if `git ls-files --unmerged` still reports any. Committed work survives; only the unfinished conflicted attempt is discarded.
- Scoped tight: the recovery matcher runs once per checkout, and every other failure (auth, network, missing refs) throws exactly as before. Covers session, task, and project reuse plus fresh-create paths — all funnel through `checkoutSessionBranchWithRetry`.
- Regression pins in `tests/sandboxReuseUnresolvedIndexContract.test.ts` keep the detector, the one-shot retry wiring, and the abort-before-reset ordering.
