# Changelog — September 2026

## Action failures users actually hit now reach the browser with a reason - 2026-09-04

- Chosen from prod (Axiom, last 14 days): `pty.connectPty` ("Sandbox is not running. Start the sandbox first."), `sandbox.getPreviewUrl` ("Vercel preview proxy failed to start on port …"), and `github.submitPrReview` (GitHub's own "Can not approve your own pull request") all surfaced as "Server Error". They now run through `runActionEffect` with tagged failures (`SandboxNotRunning` in `convex/_pty/ptyErrors.ts`, `PreviewProxyFailed` in `_sandbox_runtime/previewErrors.ts`, GitHub failures via the existing `classifyPrActionFailure`); infrastructure calls stay defects and stay redacted. Their six web callers (`TerminalPanel`, `useSandboxPreview`, `CustomTabPanel`, `SandboxIframeService`, `PrVerdictDialog`, `SubmitReviewPopover`) read the message through `convexErrorMessage`.
- Rate-limited 403 misreport fixed: `_github/userAuth.ts` said "Not authorized to inspect this installation" and `_github/prDiff.ts` said "too-large" for a throttled GitHub call. Both now branch on `classifyGitHubFailure` tags — throttling gives "GitHub rate limit reached — try again in a minute" in the first case and rethrows in the second (a "too-large" answer would have been written to the ActionCache as a permanent result). 404 and non-throttled 403 behave as before; the private zod status shapes are gone.
- Web tone mapping: `convexErrorPresentation(error, fallback)` returns `{ message, tone }` from one tag→tone table, so outcomes that are not failures (`GitHubBranchNotAhead`, `GitHubPullRequestAlreadyExists`, `RecapAuthorNotRecapped`, `RecapPrUrlInvalid`) render `text-muted-foreground` instead of `text-destructive` in `TaskFooter`, `ProjectDetailClient`, and `PrRecapPanel`; the truncating header variant gains a `title` with the full message.

## Effect adoption step 5: provider parsers on Schema, agent-stream boundary complete - 2026-09-04

- `claudeParseLine`, `codexParseLine`, `cursorParseLine`, `opencodeParseLine` (and the matching `onStreamLine` hooks) in `callback-src/providers/` were the last hand-narrowed step between raw provider JSON and `CanonicalEvent`. Each message shape is now a colocated `Schema.Struct` decoded with the non-throwing `decodeUnknownOption`, with per-field `lenient()` so a bad field yields `undefined` instead of dropping its siblings — a malformed line can never throw and never loses data the old code kept.
- The Phase 2 helpers (`lenient`, `Text`, `OptionalText`, `TextArray`) moved from `sdkTaxonomy.ts` into `callback-src/parse/schemaHelpers.ts`, plus `NonEmptyText` (non-empty, kept verbatim) which replaced five private copies across the providers and `toolResultCapture.ts`.
- Behavior verified byte-identical by differential harnesses running old and new modules side by side over every fixture line and ~158k adversarial payloads (Claude/Codex 92k incl. `onStreamLine`; Cursor/OpenCode 66k incl. `probeCursorSdkToolResult`), comparing returned events and the full `callbackState` snapshot. 24 permanent tests distilled from that, all of which also pass against the pre-conversion modules.
- Deliberately still hand-rolled: `event.type` dispatch, freeform tool-input passthrough to `toolCallToStep`/`cursorSdkToolToStep`/`opencodeToolToStep`, and `String(...)` coercions of arbitrary JSON — Schema would erase the JSON types those helpers need.

## Effect adoption step 4: tagged errors cross the Convex wire - 2026-09-02

Production Convex redacts a thrown `Error` to "Server Error", so most action failures reached the user with no reason. `convex/_effect/action.ts` adds `runActionEffect(effect, label)`: a declared failure (Effect `Fail`) is logged and rethrown as `ConvexError` with data `{ tag, message }` (`tag` = the error's `_tag`; underscore-prefixed Convex fields are not allowed), while a defect (`Die`) is rethrown unchanged and stays redacted — a bug is not a user-facing outcome. The payload contract lives in `@eva/shared/convexErrorPayload` (zod) and the web's `convexErrorMessage` now parses it, plus a new `convexErrorTag` for branching on failure kind instead of message text. Pilots: `createTaskPr`/`createProjectPr` (node) replace the string-only `withVisiblePrFailure` — every previously visible message is still visible, GitHub-shaped ones now carry their specific tag via `classifyPrActionFailure`; `docs.generatePrRecap` (first V8-isolate module to load effect) makes its three refusals visible as `RecapNotAuthorized` / `RecapPrUrlInvalid` / `RecapAuthorNotRecapped`, and `PrRecapPanel` routes through `convexErrorMessage` so it shows the message rather than a JSON blob. Measured isolate cost: `docs.ts` bundle 1.49MB → 2.02MB (+492KB of effect, shared across isolate modules that import the runner). Deliberately no `customAction`-based `effectAction` wrapper: the runner composes with the existing `authAction` without fighting convex-helpers generics.

## Effect adoption step 3: git and GitHub failures classified once into tagged errors - 2026-09-02

The retry pipelines in `git.ts` and `taskWorkflowActions.ts` each re-derived "what kind of failure is this?" from message text at every site (`isRetryableGitNetworkError`, `isNonFastForwardPushError`, `isMissingRemoteRefError`, `isPullRequestAlreadyExistsError`, `isBranchNotAheadCompare`). Two new classifiers own those rules now: `convex/_git/gitErrors.ts` (`classifyGitFailure` → `GitNetworkError | GitNonFastForwardError | GitMissingRemoteRefError | GitCommandError`, from sandbox git stderr) and `convex/_github/githubErrors.ts` (`classifyGitHubFailure` → `GitHubPullRequestAlreadyExists | GitHubBranchNotAhead | GitHubRateLimited | GitHubUnauthorized | GitHubForbidden | GitHubNotFound | GitHubRequestFailed`, from octokit, plus `githubRequest` as the Effect boundary for octokit calls). `Effect.tryPromise` catches classify at the boundary, retry `while` clauses match on `_tag`, and `Effect.mapError(cause)` at each edge still rethrows the original error object so `instanceof`/message checks in callers are unaffected. `_git/remoteRef.ts` folded into `gitErrors.ts`; `prErrors.ts` predicates are now `_tag` checks. Equivalence with the old predicates is asserted in `tests/gitErrors.test.ts` and `tests/githubErrors.test.ts` by running the old predicate bodies as fixtures over a corpus. `no-underscore-dangle` now allows `_tag`, `_id`, `_creationTime`.

## Cursor turns no longer stall on resume: SDK agent store moved from JSONL to SQLite - 2026-09-03

- Symptom (prod, sessions 174 and 176, 3 Sep 19:17–19:24 UTC): every grok-4.6 turn after the first failed with `Cursor stalled while starting the model run for 60 seconds` — once, then again on the same-agent retry, then the turn died, ~123s burned per failed turn. The failing phase was `Agent.send()` on a resumed agent inside `runCursorSdkAttempt`.
- Root cause: the store, not Cursor. Eva persisted agents with the SDK's `JsonlLocalAgentStore` at `CURSOR_SDK_STORE_DIR`, which re-reads and JSON-parses the entire file on every `get` and rewrites it whole (tmp + fsync + rename) on every `append`/`create`/`update`, with checkpoint blobs base64-encoded inside `checkpoints.ndjson`. A resumed `send()` hydrates the conversation blob by blob: in an end-to-end reproduction against the real pinned SDK, a resume after a 12-tool-call first turn issued 56 `checkpoints.get` calls before returning the run handle, against a `checkpoints.ndjson` already 793 KB. Blob count and file size both grow with the conversation, so resume was quadratic in conversation length. Session 174 had ~580 tool steps over its first three turns, which extrapolates to thousands of full-file reads of a file in the hundreds of MB. A micro-benchmark of the JSONL store measured ~1.2s per `get`/`append` at 168 MB of events plus 427 MB of checkpoints. The same per-step pattern (2 gets + 2 creates per tool step, each a full read or rewrite) also taxes every step of a long first turn.
- `runCursorSdkAttempt` (`callback-src/providers/cursorSdk.ts`) now opens the SDK's own `SqliteLocalAgentStore` at the same `CURSOR_SDK_STORE_DIR` (`stateRoot`, `workspaceRef: WORK_DIR`), per attempt, disposed in the `finally` beside `agent.close()`. It loads from the pinned SDK's separate `dist/esm/sqlite.js` entry through `resolvePinnedSdkEntry` and a second memoized loader, kept apart from `loadCursorSdk` because that entry exists precisely so the main one does not pull in the sqlite driver. Same reproduction, SQLite store: the resumed `send()` returned in 24ms with every store call at ~0ms. No timeout, retry or `agent_not_found` logic changed.
- Migration: none, deliberately. The SQLite layout is `index.db` plus `agents/agent-<sha256>/store.db`; legacy `*.ndjson` files sitting in the directory are ignored. A session whose agent id was saved before this deploy resumes as `agent_not_found`, and the existing `canReplaceCursorAgent` recovery starts a fresh agent once with the usual "Started a fresh Cursor agent" notice. Reading those legacy files is the slow path being removed, so migrating through it would reintroduce the stall.
- Tests: `tests/providerSdkDependenciesContract.test.ts` pins `SqliteLocalAgentStore` against the pinned `@cursor/sdk` 1.0.28 sqlite bundle, pins the entry path and the `open({ stateRoot: CURSOR_SDK_STORE_DIR })` call in the loader, and asserts that neither the loader nor `convex/_sandbox_runtime/callbackScript.generated.ts` mentions `JsonlLocalAgentStore` — so a stale bundle fails the build. Callback bundle regenerated.
- Operational note: `node:sqlite` prints an `ExperimentalWarning` on stderr under Node 24. It is harmless and does not reach the turn output.

## Publish merges foreign remote commits instead of calling them a rewrite - 2026-09-03

- Root cause (prod, quick task 220 / task m57dve3m, evalucom/carepulse-ts, 2 Sep 13:57 UTC and 3 Sep 08:15 UTC): both "Failed to publish task branch" alerts came from `divergedPublishLooksLikeRewrite`, the file-count classifier added for task 231. The agent never rebased. Its `git status` at the start of the 3 Sep turn read "ahead 1, behind 118": GitHub had gained 118 commits on the PR branch (a base merge landed there while the sandbox was stopped) and the sandbox had one small commit. "Many remote-only files vs few local" fired ("532 vs 1", then "90 vs 52" after the agent merged main), so publish refused a divergence that a plain merge resolves. #708's diagnosis ("the agent rebased onto a new base") was wrong; its reflog check was right but only ran after the classifier and could only refuse, never merge.

Remote tip not in the reflog: someone else pushed those commits, however many files they touch, and they are merged in as before task 231's change. The three `merge-base`/`diff --name-only` calls are gone; the log line and the merge-failure message now carry the remote-only and local-only commit counts from `rev-list --left-right`, which the prod logs lacked.
- `divergedPublish.ts` drops `REWRITE_REMOTE_ONLY_FILE_THRESHOLD`, `remoteOnlyChangedFileCount`, `divergedPublishLooksLikeRewrite` and the `RewrittenBranchRefusal` union; `rewrittenBranchPublishError(branchName)` is the single remaining refusal. The callback-side `persistTurnWork` (`callback-src/runtime/turnPersist.ts`) mirrors the rule with `localBranchRewroteOwnHistory`, skipping its merge only when the reflog holds the remote tip. Callback bundle regenerated.
- Tests: `rewrittenBranchPublish.test.ts` now expects a reviewer's commit on the PR branch, and a commit that lands mid-publish, to be merged and pushed rather than refused, and adds the quick task 220 shape (one local commit vs 30 foreign commits over 60 files) publishing cleanly. `forcePushRecoveryContract.test.ts` and `sessionPublishContract.test.ts` pin reflog → ownership → lease → merge with no file-count classifier in front; `divergedPublish.test.ts` covers the surviving helpers.

## Session turns no longer hang on "Working…" after a daemon respawn - 2026-09-02

Prod session 166 (sandbox white-advisory-iguana-fez4UA, 21:00 UTC): a prewarm launched the warm Claude daemon, a second prewarm one second later saw "model/tools changed" and killed it, the relaunch reported "runner ready" in 827ms, and then nobody polled `claimPendingTurn` for the whole turn. Three independent defects lined up:

- `AGENT_PROCESS_LIVENESS_COMMAND` (`_sandbox_runtime/lifecycle.ts`) ran `pgrep -f 'claude-code|…'`, but every exec is wrapped in `bash -lc "<cmd>"`, so the pattern matched the wrapper's own cmdline and `verifySandboxLiveness` could never report a dead callback on a running VM. The stall watchdog took `agent_process_running_callback_pid_stale` as confirmed alive, touched the streaming row and reset the staleness clock every cycle, so the turn would only die at the 2h backstop. Each alternative is now bracketed (`[c]laude-code`, `/[.]claude/`), the same trick `KILL_PRIOR_AGENT_PROCESSES_CMD` already used. Pinned by `tests/agentLivenessPgrepSelfMatchContract.test.ts`, which builds a RegExp from the source pattern and checks it rejects `bash -lc <pattern>` while still matching real agent cmdlines.
- `buildKillEntityDaemonCmd` (`_sandbox_runtime/daemonPaths.ts`) sent one SIGTERM to the daemon pid. The daemon boots its `query()` at startup, so its Claude CLI child was orphaned holding the inherited `flock -n -E 217` fd, and the relaunch lost the spawn lock. It now collects descendants with `pgrep -P`, signals the root first (the daemon has no SIGTERM handler, and killing the child first would let it post a bogus "daemon failed" completion), recurses into the children, waits up to 3s per pidfile for the root to exit, then escalates to SIGKILL. Worst case ~6s inside the callers' 10s exec budget. `tests/killEntityDaemonTreeContract.test.ts` pins the string contract and runs the generated command against a real two-level process tree.
- `launchScript` (`_sandbox_runtime/launch.ts`) relied on the detached launcher's own `rm -f` to clear `/tmp/run-design.ready`, but `execDetached` returns before the script runs, so `waitForRunnerReady`'s first poll could accept the killed predecessor's ready file. The markers (`.pid`, `.ready`, `.done`) are now removed synchronously via `execHandle` before the detached spawn; `.done` is included because `CALLBACK_LIVENESS_COMMAND` requires it absent. Ordering pinned in `tests/spawnLockIncumbentContract.test.ts`.

## Turn prewarm no longer kills the page-open daemon over an explicit default effort level - 2026-09-02

The respawn that triggered the hang above was itself a bug: Axiom shows 65 "model/tools changed — respawning" events against 146 daemon launches in 24h.

- Root cause: the composer (`useSessionSend.ts`) sends `...executionTraits` (defaults omitted) but then overrides `reasoningLevel` with the display value, so a Fable session's `startExecute` arrives with `reasoningLevel: "high"`. `stageAndStartSessionTurn` forwarded that verbatim into its own `prewarmSessionDaemon` call and into the `sessionExecuteWorkflow` args (which the workflow forwards to a second prewarm). The page-open prewarm (`prewarmDaemon`) normalises the stored traits through `launchTraitsFromStored`, which drops the model default, so its daemon opts sig had `||` where the turn's had `|high|`. Same model, same tools, different sig, kill+relaunch one second after boot.
- `stageAndStartSessionTurn` (`_sessions/execution.ts`) now runs the incoming traits through `launchTraitsFromStored` once and spreads the result into both launch call sites. The session's sticky `last*` fields still store the raw composer values. `retryEmptyStalledSessionTurn` passes the stored values raw since the callee normalises. The other two doors into `sessionExecuteWorkflow` had the same defect and were fixed the same way: the queued-message drain (`_queues/helpers.ts`, which stores the composer's explicit default) and the orchestrator wake-up (`orchestratorNotify.ts`, which forwarded `master.last*`). `getDaemonPrewarmData` already normalised.
- Task chat and project chat had the identical defect (14 `prewarmEntityDaemon` respawns in 7 days): their `startExecute` mutations (`agentTaskChatWorkflow.ts`, `projectChatWorkflow.ts`) and their queue drains in `_queues/helpers.ts` forwarded the composer's raw traits into `prewarmEntityDaemon` and the workflow start, while their page-open prewarms normalised. All four now spread `launchTraitsFromStored(...)`. The web composers still send the display effort level on purpose: the user bubble and the queued-messages panel render "Model · High" from it, and the server now ignores it for launch purposes.
- The respawn log in `runPrewarmEntityDaemon` now prints `have=<on-disk sig> want=<launch sig>` so the diverging field is visible next time. The read is one extra exec on the rare mismatch path only.
- Pinned by `tests/sessionTurnLaunchTraitsContract.test.ts` (normalisation precedes every `sessionExecuteWorkflow` start and no raw trait field reaches the args) and a `launchTraitsFromStored` case with session 166's exact payload.

## Warm daemons survive page opens; task chat cannot double-run a prompt; fresh sandboxes stop reinstalling the seeded toolchain - 2026-09-02

Investigation of "Claude/Cursor take ~30s to start" in sandbox chats (session 159, carepulse task 219). A brand-new session's first turn is expected to take ~24s before the claim (Vercel VM boot ~11s, then the claim is withheld until checkout and `pnpm install` finish) plus model time-to-first-token (~13s for Fable 5.1 at effort high). Three things were not expected:

- **Opts-signature mismatch killed warm daemons on every page open.** The composer sends traits through `buildTraitsExecutionPayload`, which omits model defaults (Claude and grok-4.6 default reasoning "high") and omits `fastMode` for models without the Fast trait; the page-open prewarms (`prewarmDaemon`, task/project `prewarmChatDaemon`, `getDaemonPrewarmData`/`getChatPrewarmData`, `retryEmptyStalledSessionTurn`) forwarded the stored `last*` values verbatim. `buildDaemonOptsSig` then differed (`…|high|…|0|…` vs `…||…||…`), so each page open logged "model/tools changed — respawning" and the next send respawned again (47 respawns and 150 mid-turn deferrals in 3 days; session 126 paid a 4s claim wait plus a cold CLI init per reopen). All those sites now go through one new helper, `launchTraitsFromStored` (`_validators/aiModels.ts`), so every prewarm computes the same signature as the turn path. Existing daemons launched by a page open mismatch once after deploy and respawn when idle. Tests: `tests/launchTraitsFromStored.test.ts`.
- **Task/project chat re-staged a claimed prompt and could run it twice.** The execute workflow's `ensurePendingTurn` (cancel-race recovery) only checked "no `pendingTurn` and an unfinished placeholder", which is also true right after the daemon claims, so a duplicate prompt sat staged for the whole turn. `shouldDeferDaemonRespawn` deliberately does not defer while a prompt is staged, so the page-open mismatch above killed task 219's Cursor daemon mid-turn, the replacement claimed the duplicate and the same "merge staging" prompt ran twice in parallel (two `handleCompletion` calls, 13:14:53 and 13:14:58). Sessions were immune via the `turns` row; tasks and projects now stamp `pendingTurnClaimedAt` (optional field on `chatDaemonEntityFields`) in `claimPendingTurn`, and `ensurePendingTurn` skips when the stamp is at or after the current placeholder (`_chat/pendingTurnRestage.ts`). Cleared in `saveResult`, `handleCompletion` and `cancelExecution`. Tests: `tests/pendingTurnRestage.test.ts`.
- **Every fresh sandbox reinstalled the Claude CLI and Agent SDK.** The seed installs with `sudo npm install -g` into node's prefix (`/vercel/runtimes/node24/lib/node_modules`), but `globalNpmRoot()` in the callback, `ensureClaudeCliAvailable` and the seed's own `globalPackageIsVersion` probed `npm root -g` as the unprivileged sandbox user (`~/.global/npm/lib/node_modules`, pnpm only), so the pinned CLI read as "unknown" (~2.5s reinstall on the launch path) and the Agent SDK was npm-installed into `/home/eva/.eva-agent-sdk` on every boot (~4.6s on the daemon boot path). `globalNpmRoots()` now tries the node-derived prefix root first, then `npm root -g`; all exact-version checks are unchanged. Bundle regenerated. Operational note: the current snapshot holds Agent SDK 0.3.201 against the 0.3.258 pin, so the SDK reinstall persists until a reseed; the CLI and `@cursor/sdk` probes hit immediately.
- Not changed: Cursor's 60s first-visible-event budget. Task 219's two 60s stalls on the resumed agent were on Cursor's side; shortening the budget trades false retries for latency.

## Cursor turns no longer die on a slow fresh-agent creation - 2026-09-02

- Root cause: the Cursor SDK validates the configured model id inside `Agent.create`/`Agent.resume` with its own `listModels()` call to api2.cursor.sh — a second round trip for a list Eva has already fetched in `resolveCursorModelSelection`. In prod two turns in a row lost their saved agent's `send` to the 60s stall, retried the same agent, stalled again, and then the fallback `createFreshAgent()` blew the 30s `CURSOR_AGENT_SETUP_TIMEOUT_MS` on that redundant fetch and killed the turn ("Cursor stalled while creating a fresh agent for 30 seconds"). The next turn took the same path and created in 12s, so the fetch, not the SDK, was the variable.
- `resolveCursorModelSelection` (`callback-src/providers/cursorSdk.ts`) now publishes the list it fetched into `CURSOR_SDK_LOCAL_MODEL_CATALOG_JSON` (new `CURSOR_SDK_LOCAL_MODEL_CATALOG_ENV` constant, serialized by the new pure `cursorModelCatalogJson`), which the SDK reads in place of its own fetch — so agent setup has no remote dependency left. A failed or unavailable list leaves the var untouched and the SDK falls back to fetching; an empty list or an entry without a string `id` is never published, because the SDK rejects a malformed catalog non-retryably.
- `Cursor.models.list()` itself now runs under `waitForCursorPhase` with a new `"fetching the model list"` phase and the same 30s deadline. It had no deadline at all, so a hung list could burn the turn before agent setup started; a timeout is absorbed by the existing catch as an unavailable list.
- `createFreshAgent` retries once when creation stalls, via the new exported predicate `shouldRetryStalledCursorCreate` (mirrors `shouldRetryStalledCursorResume`). A creation that never returned a handle holds no context, and it is the last resort of a turn whose saved agent already stalled twice. Any other error, or a second timeout, propagates unchanged.
- Callback bundle regenerated. Tests: `callback-src/tests/cursorSdk.test.ts` covers `shouldRetryStalledCursorCreate` and `cursorModelCatalogJson`; `tests/providerSdkDependenciesContract.test.ts` pins the undocumented env var name against both the pinned `@cursor/sdk` 1.0.28 bundle and our constant, so an SDK bump that renames it fails the build instead of silently restoring the network call.

## Publish recovers from a rewritten sandbox branch instead of failing the turn - 2026-09-02

- Root cause (prod, task m57dve3m, evalucom/carepulse-ts, 2026-09-02 ~14:17 UTC): the agent rebased its `eva/task-…` branch onto a new base, so `synchronizeBranchForPublish` classified the divergence as a rewrite ("532 remote-only files vs 1 local") and threw. That was the right call for task 231's shape, but the refusal had no automatic way out: `pushSandboxBranch` failed hard three times, `agentTaskChatWorkflow` posted the raw error, and the task chat — unlike sessions — has no force-push banner, so the PR could never be updated even though GitHub only held the sandbox's own old tip.
- `synchronizeBranchForPublish` now, on the rewrite branch only, reads the exact remote tip and the local branch's reflog (`git reflog show --format=%H refs/heads/<branch>`). If the branch is `eva/`-owned and the remote tip is a commit the local branch itself once pointed at, the remote holds nothing this sandbox never had, so it returns `replaceRemoteTip` and `pushBranchToOrigin` pushes with `--force-with-lease=refs/heads/<branch>:<that sha>` — never a bare `--force`. A commit that lands in between is rejected as "stale info" (now matched by `isNonFastForwardPushError`), and the retry re-syncs against it; a tip missing from the reflog refuses as before.
