## Sandbox git token cache follows the real token expiry - 2026-11-05

## Run, automation and sandbox lifecycle follow-ups; web race fixes - 2026-11-03

- A task run now owns only its task's `in_progress` status. `completeRun`, the 2h `handleStaleRun` watchdog and `cancelExecution` no longer overwrite a status the user picked mid-run. The watchdog now keys on `activeWorkflowId`, not on `in_progress`, so it still times out a run whose task was moved.
- Automation run `success` / `error` / `cancelled` are final (`_automations/runStatus.ts`):
  - `updateRunStatus` and `settleEventRun` ignore writes after a terminal status, so a late success can no longer turn a cancel into a success email.
  - `settleEventRun` still advances `eventCursor`.
  - `cancelRun` does nothing on a finished run. Otherwise it closes the agent turn and deletes the ephemeral sandbox, because a cancelled workflow skips its own `finally`.
- Sandbox starts:
  - New sessions boot with attempt 1.
  - Every start request schedules its own failure write 20 min later (`STUCK_STARTING_EXPIRE_MS`). A start whose action died now closes with "Sandbox start timed out. Press Start to retry."
  - A tokened ready that lands after Stop or archive deletes the fresh VM only it made. Untokened prepares (such as `sessionExecuteWorkflow`) keep theirs.
  - An untokened `projectSandboxStarting` (the project interview) may restart a closed sandbox again. This undoes an earlier over-tight guard.
  - Chat release marks a session `closed` only if it is still `active`, and marks its background processes exited.
- Web:
  - Merge and Revert ignore clicks while in flight, and the Merge dialog cannot be closed mid-merge.
  - Force-push marks the offer requested at once and un-marks it on failure.
  - The doc version save keeps edits typed during the save counted, so it no longer shows "saved" over them.
  - `SandboxIframeService` drops results from a start that Stop superseded (a generation counter, as in `CustomTabPanel`). It only cancels polling when the sandbox changes or the panel unmounts.
  - Composer stash and restore share one lock. Stash clears the text up front and puts it back on failure, and removes only the stashed files.

- Deleted `taskWorkflow.triggerExecution`. It had no callers, no access check, and accepted any `repoId`, so it could run a task's prompt against another team's repo.
- New `getDocWithAccess` (`functions.ts`) sits beside the session and project helpers.

"Running" is read from `workflow.status`, so a slot left by a crashed workflow does not block for the 2h watchdog.

## Lifecycle guards for sandboxes, project phase and run status - 2026-11-02

- Deleted five public mutations with no callers that let any client set a status directly: `agentRuns.updateStatus`, `agentRuns.complete`, `sessions.updateStatus`, `sessions.updateSandbox` and `sessions.clearSandbox`. `clearSandbox` dropped `sandboxId` without stopping the VM.
- `recomputeProjectPhase` counts `todo` and `in_progress` tasks as not done again (lost in ec467f624), so one done task no longer completes the project. `completed` and `cancelled` now leave only when a new build starts, not after a task status edit.
- New `_sandbox/transitions.ts` holds the sandbox rules for sessions, tasks and projects. A start request is skipped while the sandbox is `stopping`, and the post-stop drain wakes it again. A start failure closes the sandbox only while it is still `starting`. `projectSandboxStarting` and `projectSandboxAllocated` no longer revive a stopped project; `Allocated` still records the VM id.
- Each start request bumps a new `sandboxStartAttempt` field on sessions, tasks and projects, and passes the number through the startup workflow and action. Ready, failure, `projectSandboxStarting` and `projectSandboxAllocated` writes from an older attempt are ignored. If that older attempt made its own VM, the VM is deleted; a VM shared with the current attempt is kept. Starts with no number (first session boot, the project interview, jobs scheduled before this deploy) keep the status-only rules.
- `markTaskSandboxStartingForChat` no longer turns `stopping` into `starting`. Its return value is unchanged, so journaled workflow runs replay as before. The start action then aborts, and the chat turn reports "did not become ready".
