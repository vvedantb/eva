## Sandboxes and cache Drives move to iad1 - 2026-11-13

WHY: Vercel's rates for Active CPU, memory and Drives in iad1 (Washington, D.C.) are about 30% under cdg1 (Paris) and lhr1 (London), as checked for PR #1260 on 2026-11-13.

- `SANDBOX_REGION` is `iad1` again (it was `cdg1` from #899). Failover is now `cle1`; a failed-over sandbox runs without its Drive.
- Each repo gets a new `eva-iad1-<repoId>` Drive. The Drive starts empty and the next seed build fills it. The `eva-cdg1-<repoId>` Drives made since the earlier deploy today, and the old `eva-<repoId>` Drives, are unused; delete them by hand in the Vercel dashboard.
- Seeded snapshots made in cdg1 cannot move: `sandboxPlacement` keeps starting a repo's sandboxes in cdg1, without a Drive, until that repo is seeded again. Seed every repo again to finish the move.
- Sandbox data now sits in the US. Convex prod stays in eu-west-1.

## Snapshot seeds fail fast when the local Convex backend dies - 2026-11-13

WHY: CarePulse eprocurement seeded builds have failed every day since at least 28 Oct. The local backend is healthy at the readiness gate, then stops answering during the staging import. The seed hung until the workflow timeout ("state: running"), and the 4 KB log tail held only `convex dev` retry lines.

- `fetchSeedDiagnostics` adds a memory section and keeps 16 KB of `seedrun.log` (was 4 KB).

## Cache Drive mounts again; low disk frees Eva caches; full disk says so - 2026-11-13

WHY: From 2026-10-07, every sandbox skipped its cache Drive: the Drives were in iad1, sandboxes moved to cdg1, and `Drive.getOrCreate` failed with "409 already exists in a different region" (152 skips for 161 creates, 4–11 Nov). The package cache then sat on local disk, 5.2 GB of it baked into seeded snapshots. Session 96's sandbox (32 GB disk) ran a week near 1.4 GB free, then filled, and the agent daemon failed with a bare "ENOSPC: no space left on device, write".

- `driveCacheName` is now `eva-<SANDBOX_REGION>-<repoId>`, so each repo gets a new `eva-cdg1-<repoId>` Drive in the region its sandboxes run in. The Drive starts empty and the next seed build fills it. `SANDBOX_REGION` stays `cdg1`: the move back to iad1 from PR #1260 is not part of this change. The old `eva-<repoId>` Drives (iad1, last written about 2026-10-07) are unused; delete them by hand in the Vercel dashboard.
- `localCachePruneLines` (`driveCache.ts`) empties `/eva-cache` when it is a plain local directory (never when a Drive or overlay is mounted, and never `npm/_npx`). The snapshot prune uses it, so seeded snapshots stop carrying the cache.
- `lowDiskCleanupLines` (`sandboxFiles.ts`) runs that prune and empties Eva-owned `/tmp` logs over 64 MiB when free disk is under 2 GiB (`LOW_DISK_CLEANUP_MIB`). It runs at the start of the swap script (every boot path) and in the disk-full reclaim after a failed file write. It never touches the repo, build output, `node_modules` or local database data. The swap log line shows `low-disk-cleanup before=… after=…`.
- `assistantReplyContent` turns an ENOSPC failure into "Error: Sandbox disk is full. Free space in the sandbox (…) and start it again." and keeps the raw error below. `SandboxDiskFullError` uses the same advice text (`SANDBOX_DISK_FULL_ADVICE`).
- The `driveCache.ts` header no longer calls the reader overlay "tmpfs-backed": its upper dir is on local disk in `/var/tmp`.

## Find and fork reach older history from the server - 2026-11-11

WHY: With paged history, find and fork loaded the whole chat on use.

- New `messages.searchOlderByParent` (search index `search_content` on `messages.content`, filter `parentId`): the oldest match above the loaded rows. Find waits 350 ms after typing, asks it, and `useOlderTranscript` loads down to that row; the bar then counts, highlights and jumps as before. A query with no older match loads nothing.
- Server search matches whole words and word starts (agreed). Substring-only matches are still found in the loaded rows. It reads the top 50 hits by relevance, so a very common word may not reach its oldest match.
- New `messages.forkPrefixByParent` builds the fork prefix with the shared `collectForkPrefix`, so fork no longer loads history.
- `TranscriptReach` is `{ messageId }` or `{ search }`; the "all" target is gone. `isReachingHistory` tells ChatBody when a jump is done or out of range.
- `ThreadFindBar` takes `jumpKey`, so it jumps again once rows loaded for its query render.

## PR descriptions get a merge-risk score and a Rollback section - 2026-11-11

- Every PR Eva opens, in any repo, now gets a "Merge risk: Low / Medium / High" block at the top of its description. `_github/mergeRisk.ts` scores it with fixed rules, no model, so the agent that wrote the change cannot talk the score down.

## Heavy sessions open from the newest 30 messages - 2026-11-10

- `messages.listByParent` takes an optional `tail`. With it, the query reads only the newest `tail` messages, so its cost does not grow with the chat.
- New `useChatTranscript` hook (`apps/web/src/lib/hooks/`). A chat paints from the tail (30 messages), then takes the full list. Sessions, quick tasks, projects, the subagent roster and the hover prefetch use it. Row ids are the same in both results, so nothing moves when the full list lands.
- The session chat now shows the transcript loader while messages load. It showed "No messages yet" before.
- Load test: the focal chat now carries activity logs sized like production (mean 25.6 KB per assistant message), and 18 `session open` cases cover the queries a session page subscribes to.
- Measured on a 400-message chat (5.6 MB): the query the chat paints from went from 184 ms and 3.1 MB returned to 43 ms and 0.29 MB (30 samples each, Mann–Whitney p < 0.001). The tail reads 34 documents and 0.52 MB at every scale up to 40,000 messages. In Chrome (dev build, cold data), click to last turn on screen went from 787 ms to 520 ms locally and from 1,590 ms to 728 ms at 20 Mbit/s (n = 16 each, p < 0.001).
- Not fixed: the full list still reads the whole chat. It fails at Convex's 16 MiB read limit at about 1,200 messages of this size, and the chat page still errors. The fix is to store activity logs outside the `messages` row, or to page the history.
- Method limit: local server time of the tail still grows with the chat (227 ms at 4,000 messages), because any read in a large index range is slow on the local backend, even `take(1)`. Convex cloud was not measured.
- Deploy notes: none. `tail` is optional, so old clients keep working.

## Auto-continue once when a chat turn hits the runtime cap - 2026-11-10

- When a session, quick-task chat or project chat turn fails at the 3-hour cap, the turn-end queue drain (`startNextQueuedChatMessage`) puts one continue message at the front of the queue (`queueRuntimeContinue` in `_chat/runtimeContinue.ts`). The chat shows "Continue: the last turn hit the 3-hour limit."; the agent gets a prompt to resume from git.
