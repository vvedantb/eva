# Changelog — October 2026

## Agents render HTML pages inline in chat with `render_html` - 2026-10-07

- New MCP tool `render_html` (modelled on t3code's `html_render`), on every session, quick task and project sandbox token. The agent sends one self-contained page (`html` ≤ 900 KB UTF-8, `title`, `height` 80–2000 px), and the page shows under its turn. `render_ui` stays for structured panels; the chat prompt nudge now names both tools.
- Storage: `chatHtmlRenders` (meta, `by_parent`) plus `chatHtmlRenderBodies` (the page). `listByParent` never reads pages; `chatHtml.getHtml` loads one page per mounted frame, auth-checked through its render row. Fork copies the meta rows and shares the body.
- `ChatHtmlFrame` shows the page in a `srcdoc` iframe with `sandbox="allow-scripts allow-forms allow-popups"` (no same-origin), borderless on the chat background. `@eva/shared/htmlRender` injects a bootstrap that speaks MCP Apps method names: the theme tokens (RGB channels wrapped in `rgb()`) go in on first paint and on each light/dark switch, the page reports its height, link clicks open in a new tab through the host, and Web Storage is in memory. A fullscreen toggle (same pattern as the preview panel) sits in the top-right corner; it is always shown, because hovering an iframe gives the parent no hover state.
- Pages load through the Convex sync connection, not an HTTP-action URL: the sandbox preview proxies only `/__convex`, so a `.convex.site` page URL would break there.

## Snapshot restores follow the snapshot's region - 2026-10-07

- After #899 moved sandboxes to `cdg1`, restoring an older seed snapshot failed with "The snapshot is available in `iad1`, but this sandbox runs in `cdg1`". `VercelSandboxClient.create` now reads the snapshot's regions and creates there. If that is not `cdg1`, it skips the region-pinned `cdg1` Drive mounts. Create logs now include the region.

## Remove the "Resume with less context" banner - 2026-10-06

- The compaction offer above the composer is gone from sessions, quick tasks and projects; it was rarely used. Deleted `ComposerCompactionBanner.tsx` and the `compactionReadOnly` / `onSendCommand` fields that only it read from `SandboxChatSurface`. `/compact` still works when typed.

## Agents ask for secrets in an inline card - 2026-10-06

- `request_env_var` now posts a secret card (modelled on t3code's `SecretRequestCard`) instead of a settings link. The card has the key, the reason, a masked field, "Save securely" and "Decline". After an answer it collapses to a one-line row.
- New `envVarRequests` table (status only, never the value). `envVarRequestsActions.save` encrypts the value into repo or team env vars. Then it appends an `export` line to the live sandbox's `.eva-env.sh`: `writeFile` to a temp file, then `cat >>`, so the value never goes on a command line. The card posts a key-only reply (`_envVarRequests/replies.ts`) so the agent resumes.
- `ChatBody` places panels and secret cards through one `placeChatUiPanels` call, so all three chat surfaces get the card. `latestChatMessageId` (`_chat/chatParent.ts`) is shared with `chatUi.create`. `launch.ts` and `devServer.ts` now import `EVA_ENV_FILE` instead of redeclaring it.

## Every sandbox tab can wake Eva - 2026-10-06

- `SandboxPaneSlots` and the Files callers pass a `wake` prop (`onStartSandbox`, `isSandboxStarting`) down to each panel.

## Sandbox startup steps match t3code's setup card and show once - 2026-10-06

- New `SandboxStartupSteps` shows a shimmering "Waking Eva up…" header with elapsed time, then one row per stage: check when done, spinner while running, x on error. `StreamingActivityDisplay` uses it for every startup stream (session, quick task, project) in standard view.
- Session startup now renders only at the end of the transcript. `ChatBody`'s `emptyStateOverride` and `beforeQueuedContent` slots became one `transcriptTail` slot, so the copy above the composer is gone.
- Quick task and project sandbox chats now show the same steps at the transcript tail when waking from the header. They use the shared `sandboxStartupTail` helper and the previously unused `sandboxStartupActivity`.
- In an empty chat the tail is bottom-anchored (viewport-height `justify-end` wrapper), so the steps sit just above the composer like in a chat with messages.

## Chat queues while Eva sleeps or a usage limit holds - 2026-10-06

- The sandbox chat composer (session, quick task, project) no longer locks while the sandbox is asleep. A send queues, wakes the sandbox, and the sandbox-ready drain sends it. `sandboxComposerState` now returns `queuesSends`, and only an account swap disables input.
- Usage-limit failures stamp `messages.limitResetAt` once, at failure time (`applyChatTurnResult`). `findUsageLimitHold` holds same-provider queued messages until about 10 minutes after the reset (2-minute parse margin plus `USAGE_LIMIT_QUEUE_RESUME_DELAY_MS`), and a `drainQueueQuietly` run is scheduled for that time. Idle stop ignores a held queue, so the VM can sleep through the wait.
- One quiet drain (`drainChatQueueQuietly`) now serves enqueue, sandbox ready, the usage-limit resume and a provider switch for all three surfaces. It replaces the session-only sandbox-ready config and never wakes a watching orchestrator.
- If messages are held and the user picks a model from another provider, a confirm dialog says they will send now. `queuedMessages.switchModel` then moves the queue to that model and drains it. The queue panel heading shows "sends in …" or "sends when Eva wakes up". Shared through `useChatQueueGate`; tests are in `tests/chatQueueHolds.test.ts`.
- Not covered: a quick task's first run reports failures on `agentRuns`, not `messages`, so a usage limit hit there does not hold the queue.

## Snapshot pnpm installs no longer abort without a TTY - 2026-10-06

- Session startup failed at `newSessionSandbox.installDependencies` with `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`. `DRIVE_CACHE_ENV` moved the pnpm store to `/eva-cache/pnpm-store`, so snapshots baked with the old local store made pnpm want to purge `node_modules`, and its confirm prompt aborts with no TTY.
- New `dependencyInstallCommand` (`_sandbox_runtime/git.ts`) builds the install shell for both the fresh-clone and snapshot paths; pnpm now runs `pnpm install --config.confirm-modules-purge=false`. The `.npmrc`/env spellings do not work on pnpm 10, and `CI=true` was rejected because it implies `--frozen-lockfile`.

## Event automations: hardened after review - 2026-10-02

- One install per preset in a monorepo: `pickOnePerPreset` (`_automationEvents/select.ts`) keeps the install on the PR's own app, then the root row, so a CI failure reaches its chat once. User automations still all fire.
- Review batches are claimed (`claimEventRun`, queued → running) before they fetch, so a comment that lands mid-send queues a new batch instead of being absorbed. The next batch starts from the newest comment's GitHub timestamp (`eventCursor`), not Eva's clock. All three comment lists and check runs are now paginated.
- Every preset run gets an `expireEventRun` backstop 15 minutes after its debounce, so a crashed flush cannot block a PR or issue for good.
- Issue tasks are recorded on the run (`createdTaskId`) the moment they exist. A failure afterwards (the link comment, `WEB_APP_URL`) can no longer lead to a second task.
- A busy `run` automation now retries its event every 2 minutes for up to a day (`startEventRun`), so a burst of merges is no longer dropped.
- The CI fix count resets once the PR's head commit is fully green: `noteCiPassed` and `confirmCiGreen` check every check run before marking past attempts `superseded`.
- Preset runs settle through `settleEventRun` and never email. Their "Send email" switch is hidden, and the history now reads "Stopped CI auto-fix after 3 attempts" or "Sent 2 review comments".
- New `convex-test` coverage of dispatch, claim, expiry, retry and reset in `automationEventDispatch.test.ts`, plus web tests for the trigger copy.

It follows the Agent Memory Repo spec (github.com/AgentMemoryRepo/agentmemoryrepo), but memory lives in the code repo rather than a separate one, so edits ship in the normal PR.

## Idle sandboxes stop after an hour without chat or agent activity - 2026-10-05

- Vercel bills provisioned memory (2 GB per vCPU, so 16 GB at our 8 vCPUs) for every minute a sandbox runs, idle or not, and nothing stopped an Eva sandbox before its 24h session cap except the user or the opt-in daily sweep. New cron `sandbox idle-stop sweep` (every 5 min, `sandboxIdleStop.ts`) stops any active session, task or project sandbox whose newest chat message (user prompt, assistant reply, or a system alert such as "Sandbox started") is older than the configured idle time. A running turn, run or build, a pending handoff, or a queued follow-up counts as busy and is never stopped. Terminal or preview use that never touches chat does not count, by design.
- Each stop goes through the same path as that surface's Stop button (`requestSessionSandboxStop`, `requestTaskSandboxStop`, and the newly extracted `requestProjectSandboxStop`), so status flips to "stopping" in the same mutation and to "closed" once the provider confirms. A system alert in the chat explains the stop before the usual "Sandbox stopped" divider. The daily sweep's per-surface stops now use the same helpers instead of their own minimal patches.
- Settings → Sandboxes gains an "Idle auto-stop" section (toggle + idle time picker: 15 min to 8 h). Stored on `appSettings` as `sandboxIdleStopEnabled` / `sandboxIdleStopMinutes`; absent means on at 60 minutes, so the sweep is live from deploy. Pure rules in `_sandbox/idleStop.ts`; tests in `tests/sandboxIdleStop.test.ts`.

## Fork session stacks on the source branch and copies the transcript - 2026-10-05

- A fork used to take the source's `baseBranch` and cut a fresh branch from `origin/<base>`, so none of the source's commits were on it (carepulse-ts session 93 forked from 89 opened on `staging` with no changes). `createForkedSession` now sets the fork's `baseBranch` to the source's `branchName`, so the existing boot (`checkoutSessionBranch` → `resolveBaseTarget`) cuts the fork branch from the source branch tip and the PR targets the source branch, like a stacked PR. `forkSession` first checks the source branch exists on GitHub (`repos.getBranch`); when it does not (never pushed, or deleted after its PR merged) the fork falls back to the source's own base, the only valid PR base left. Uncommitted work on the source disk is still discarded by the `-f` checkout, as before.
- "Fork session" no longer sends the source's last turns as a `<forked_thread>` first message. The forked Vercel disk already carries every provider's persisted conversation (`/home/eva/.claude-persist` state + transcript, and the Codex/Cursor/OpenCode equivalents), so the fork's first turn resumes the source thread (`resolveClaudeSessionMode`) and the prompt replayed history the agent already had.
- `forkSession` (`_sandbox_runtime/sessionFork.ts`) now pages the source `messages` into the fork with `copyForkMessages` (40 rows a mutation, `clientId` and `pendingQuestion` dropped, everything else verbatim including `model` checkpoints, `afterSha` and storage ids), then `copyForkCards` re-anchors `proposedPlans` and `chatUiPanels` on the copies. The copy finishes before the menu navigates. `createForkedSession` also carries `planContent` and `lastInteractionMode`.
- `collectSessionForkPrefix` removed from `@eva/shared`; the per-message "Fork from here" prompt helpers are unchanged.

## Fork session (chat + sandbox/DB) replaces Duplicate - 2026-10-01

- Session right-click menus (sidebar row, archived row, Chrome tab) swap "Duplicate" (an empty "(copy)" session) for "Fork session". The fork gets the source's transcript as its first message, plus the source's repo, base, linked repos and composer traits.
- The fork's first sandbox is a Vercel `Sandbox.fork` of the source sandbox (`sessions.forkSourceSandboxId`, new `forkFrom` on `SandboxCreateParams`), not a repo-snapshot boot. Local Supabase volumes, Convex local state and untracked seed files therefore carry over, and the code checks out a fresh branch off the base as usual. Env still comes from Eva's post-create env file. A Vercel fork restores from the source's current snapshot, so `forkSession` (`_sandbox_runtime/sessionFork.ts`) stops a running source first. The source is started again only after the fork's sandbox has been taken. The fork's first boot calls `settleForkSource`, which uses the Start button's path (now shared as `requestSessionSandboxStart`). If the fork fails before the fork session exists, `forkSession` restarts the source itself. A source that was already stopped or archived stays as it was. Forking refuses while a turn is open, and the menu item is disabled with an "Agent working" hint.
- A session with no sandbox (never booted, or archived past the 48h grace delete, which clears `sandboxId`) shows Fork session disabled with a "No sandbox" hint. `forkSession` also refuses when the source sandbox is gone, instead of falling back to a chat-only fork. Only a provider "gone" verdict counts, not any lookup error. If the source is deleted before the fork's first boot, that boot clears `forkSourceSandboxId` and explains why, so the next Start boots the repo snapshot instead of failing forever.
- `messageFork` helpers moved to `@eva/shared` so the backend builds the same `<forked_thread>` prompt. The new `collectSessionForkPrefix` keeps the latest turns that fit the prompt budget.
