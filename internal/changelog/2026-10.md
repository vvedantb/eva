# Changelog — October 2026

## Sandboxes can push to sibling repositories - 2026-10-16

- Symptom: carepulse-ts session 96 resolved conflicts on a carepulse_v2 PR but GitHub refused the push ("write access not granted"). Sibling repos got a `contents: read` token by design.
- `githubAuth.getSiblingRepoInstallationToken` (was `getReadOnlyRepoInstallationToken`) now mints `contents: write` + `metadata: read`, still scoped to that one repository. No PR, issue or workflow permissions. Action renamed `mintSiblingRepoToken`; audit log tag is now `[git-credentials][sibling]`.
- Access rule is unchanged: repos the sandbox owner can reach in Eva, minus hidden, disconnected and opted-out rows. The settings toggle now reads "Usable by other sandboxes" and is the opt-out for push too. The field stays `sandboxReadExcluded` to avoid a migration.
- Prompt block is now "Other repositories you may use": push only when asked, to a feature or existing PR branch, never the default branch unless told, no force-push of others' branches. `gh` still cannot see these repos, so no PR creation there.

## Linked session groups across repos - 2026-10-16

- A session that spins up another through the MCP `create_session` tool now puts both in a linked-session group (new `sessionGroups` table, `sessions.sessionGroupId`).
- The Sessions sidebar shows each linked group as its own section above the repo groups, in both Active and Archived lists. Linked sessions leave their repo lists. Each row shows its app mark left of the title (the hover card names the app), and parallel chats stay nested under their session.
- Groups can be renamed (right-click the group header, or the header chip menu). "Remove from group" takes a session out; a group left with one session dissolves.
- The session header shows an "N linked" chip. Its menu lists every linked session, in any repo (archived ones marked), and opens it.
- MCP: `get_agent_state` returns a session's `sessionGroup` (name and members across repos). New `rename_session_group` and `remove_from_session_group` tools default to the caller's own session; Manager Ave has them too (it passes `sessionId`).
- Repo groups and linked groups now share one session row (`SidebarSessionListRow`), and each row reads its chats from its own repo.
- Session hover links (fork links and linked groups) now use the app's custom label, so names match the sidebar.

## Stop sandboxes woken after Stop - 2026-10-16

- New 10-minute leak sweep stops Vercel VMs that run while every Eva owner is closed; a background exec after Stop had silently resumed them for hours.
- Linked-repo setup retries and the Convex readiness watcher now skip once the session, task or project is stopped, so they no longer wake the VM.
- PR descriptions on a stopped sandbox now resume it briefly and stop it again; kill, stall-diagnostics and deadline jobs skip VMs that are not running.
- Patched the Vercel Sandbox SDK so commands on a stopped sandbox fail instead of silently resuming it; only an explicit start wakes a VM now.
- Upgraded `@vercel/sandbox` to 3.8.0 (3.6.1 recovers dropped command and log streams without re-running commands); the resume patch now applies to every SDK version.

## Faster session switching - 2026-10-13

- Switching between kept-alive sessions re-rendered every mounted session tree three times. Three causes, all fixed at the source:
  - `RepoProvider` subscribed to every location change, and the compiler did not memoise its context value (it came from a helper call). Every `useRepo()` consumer re-rendered on any navigation, app-wide. The value is now built inline, and passive trees subscribe to nothing.
  - The stock nuqs TanStack adapter selected a fresh object and rebuilt each setter on every pathname change, so every `useQueryState` re-rendered and passed new handlers down. `lib/nuqsTanstackAdapter.tsx` selects a query string and reads the pathname at write time.
  - `usePrTabParam`, `useDiffSearchParams` and `useSessionRouteSandboxTab` now select primitives and read the pathname inside their setters.
- The shell being hidden gets `isRouteActive = false` through `useDeferredValue`, so its re-render runs after the next session paints.
- Sandbox panes (Review, Files, Editor, Browser, Docs, Artifacts, Designs, Agents, Plan, custom tabs) mount on first view through `KeepAlivePane`, then stay mounted. Before, every session mounted all of them, including the Editor and Browser iframes.
- Hovering a session link warms its Convex queries (session, chats, transcript) through the `$numId` route loader, so an uncached session paints from cache.
- The session cache keeps 5 shells instead of 3.
- Measured on the dev build: a cached switch blocked the main thread 600–775 ms → 270–380 ms; an uncached open 670–885 ms → 350–440 ms. Components re-rendered per cached switch: about 3,800 → about 1,400.
- Long chats: every visit loaded 25 more older turns, so a heavy session grew and slowed each time it was shown. Stick-to-bottom springs down from where the backlog commit leaves the scroll, and the "earlier turns" marker fired on the way past. `ChatEarlierTurnsLoader` now ignores the marker while the chat is still locked to the bottom, while its viewport has no size, and in a hidden shell.
- Settled replies and sent messages render Streamdown in `mode="static"`. Streaming mode re-rendered every block in one transition after mount.
- `MessageAction` mounts its Radix tooltip on first hover or focus. Over a hundred tooltips each re-rendered once after measuring their anchor.
- Measured on a seeded 460-message chat (dev build): showing it again 1.1–1.7 s of long tasks (including a ~0.9 s freeze about 1.5 s later) → 0.6–1.0 s, no late freeze, about 10,500 → 1,900 renders. First open: worst task 1.0–1.2 s → 0.56 s.

## Long chats render their last 25 turns - 2026-10-13

- The transcript now renders only the last 25 user turns. Rendering every turn froze a 450-message chat for about 1.4 s on open and blocked the page for about 45% of the time while a turn streamed.
- Older turns load automatically as the reader scrolls up, and the reader's place holds with no jump. Native scroll anchoring is turned off on the transcript so only one correction runs.
- The window only grows. It also extends to cover the NEW divider, a jump-rail target (which releases stick-to-bottom first) and the first find match, so those still reach their row.
- Streaming no longer re-runs whole-transcript work: the preceding-user-turn lookup is one O(n) pass, and the jump rail builds its ticks from the stable message list, so it no longer re-queries the DOM on every token.
- Measured on a production build with a 453-message replica: open 1.4 s → 0.16 s longest block; typing p90 88 → 24 ms; 40 streaming updates 63 long tasks → 0.

## Chat Log in the Documents tab - 2026-10-12

- Each session, quick task and project now has a Log. It is pinned at the top of the chat's Documents tab (`?panelItem=log`) and holds decisions, changes, research, answered questions and notes. The idea comes from GitHub Next Chopin, which keeps decisions apart from prose so a rewrite cannot lose them.
- Storage: new table `chatLogEntries`. It is append-only and keyed by the same chat source fields as docs and artifacts. A changed decision is a new row with `supersedesId`, and old rows are never edited. The Log is never copied into `docs`.
- Writers:
  - The agent writes entries with the new MCP tools `log_entry` and `read_chat_log`. `CHAT_LOG_INSTRUCTION` in the shared turn prompt asks it to log decisions, research and changes.
  - The user writes entries with "Add note".
  - Eva writes some entries itself. `pendingQuestions.claimAnswer` logs a blocking question and its answer before it deletes the row, and `applyChatTurnResult` logs one change entry for each turn that committed.
- Agent memory: `prependModelHandoffContext` adds the Log, as markdown capped at 8,000 characters, only when a fresh provider session takes over the chat. It does not add the Log on every turn.
- Repo Documents list: `chatLog.listForRepo` returns one read-only "Log · <chat>" row per chat. Each row opens that chat's Log, and the query scans the newest 1,000 entries. Entries carry `repoId` for this (index `by_repo`).
- A turn in a parallel session chat logs to its session: `chatSourceFieldsForEntityId` maps a `sessionChats` id to its session.
- Repo deletion now deletes Log entries for every session, quick task and project.
- Markdown rendering lives in `@eva/shared/chatLog`, one renderer for the download, `read_chat_log` and the handoff block.

## Parallel chats inside a session - 2026-10-08

- A session now holds several chats that run at the same time on its one sandbox, branch and checkout: a Main chat (the session's original transcript) plus parallel chats opened from `+` in a tab strip under the chat header. Each chat has its own transcript, warm agent daemon, provider conversation, turn and composer settings (model, effort, thinking, 1M, fast, account), so one session can run Claude and Codex side by side.
- New `sessionChats` table owns what was "the chat" on the session (messages, queue, turn, daemon signals, model picks); the session keeps what is about the sandbox (status, branch, PR, preview, terminal). Every existing session gets a Main chat on first open or via `_migrations/backfillSessionChats`, and its messages move onto it. A backfilled Main keeps the session id as its Claude transcript seed so it resumes instead of starting cold.
- At most 3 chats of a session run at once. A fourth send parks on its own chat with a "waiting for a free slot" caption and starts when a sibling finishes (`drainSessionChatQueues`). The prompt gets a one-line note when more than one chat is live: other chats may edit the same checkout; do not revert their changes.
- The sidebar lists open parallel chats indented under their session (the session row is Main). Links carry `?chat=N`; plain session links still open Main. Session rows and the running count light up from open turns across all chats (`turns.sessionId`).
- Sandbox MCP token: `entityId` stays the session, and a new `chatId` claim names the daemon's chat. Panels, HTML renders, preview tool calls, env var cards and questions land on that chat; session-level tools (dev server, browser lock, PRs, docs) are unchanged. `send_chat_message` gains `chat` (number or title) for sessions and lands in Main otherwise; `stop_agent` on a session stops every chat.
- Removed the `sessionDaemonStates` mirror and the session-level `setModel` / `setProviderAccountId` / `setTraits` (now `sessionChats.*`). The table stays in the schema until the migration has emptied it everywhere.
- Deploy step: run `npx convex run _migrations/backfillSessionChats:backfillSessionChats` after deploying.

## Faster switching between long sessions - 2026-10-12

- Cause: a switch flips `isRouteActive` on two cached shells. That re-rendered `ChatBody`, and three row props got a new identity each time, so the `ChatMessage` memo failed for every row. On an 80-message chat, a switch back to a cached session blocked the main thread for about 2.4 s in dev, which was slower than opening a session cold.
- `ChatMessage.onFork` now takes the message id, so `ChatBody` passes the stable `setForkThroughId` to every row instead of a closure per row.
- `onRetryTurn` goes only to failed rows (`errorType` set), the one place Retry shows. `handleRetryTurn` changes with `onSend`.
- `SessionDetailClient` and `TaskDetailInline` declare the Agents/PRD tab handlers outside the panel JSX. Inline, the compiler rebuilt them with the whole block on every switch.
- `useComposerCompact` skips its layout reads when the draft is empty or has files. In that state the result needs no measuring, and the read forced a whole-page layout during render.
- Result (dev, 3 seeded 80-message sessions): median main-thread block on a warm switch went from 2370 ms to 780 ms, with 0 row re-renders. A cold switch (session not in the 3-shell cache) is unchanged at about 1 s for first paint. Its main cost is mounting markdown and Radix tooltips.

## Persistent state for hosted artifacts - 2026-10-12

- Artifacts were stateless: the shim's `localStorage` is in-memory, so all data was lost on reload. Artifacts now get `window.cowork.state` (`ready`, `get`, `all`, `set`, `remove`, `subscribe`), stored in Convex, so they can work as small apps.
- New table `artifactState` (`artifactId`, optional `ownerId`, `key`, JSON-text `value`). Scope `user` is private to each viewer; scope `shared` is one copy for the bound team. Limits: 200 keys per scope, 64 KB per value. `artifacts.remove` now deletes the state rows too.
- New `artifactState.list/set/remove`, gated by team membership. The bridge pushes the live snapshot into the iframe on every change, so other viewers' writes arrive in real time. Writes use optimistic updates.
- `useArtifactBridge` now parses iframe messages with Zod, and every request is answered with one `eva-result` message type. Tool args cross the bridge as JSON text. The `create_artifact` tool description documents the state API for agents.
- Rejected: a server-side isolate (QuickJS or Vercel Sandbox). The iframe already runs the app logic; only persistence was missing.

## Composer predictions (experimental) - 2026-10-09

- New experimental flag `composerPredictions` (Settings → Experimental, off by default). It follows Codex "composer predictions": when the agent finishes a turn, the empty composer shows the likely next user message as ghost text. Tab inserts it, Escape dismisses it, and it never sends on its own.
- New action `textGen.predictNextMessage({ parentId })`. It checks chat access through `composerPredictionContext.getPredictionTarget`, which returns the newest non-system message only when it is a finished assistant reply without an error or open question. An `ActionCache` keyed on that reply id means one model call per reply across tabs and viewers.
- Client hook `useComposerPrediction` runs only for the on-screen chat (`isRouteActive`), while the agent is idle and the draft is empty. It shares the `data-suggestion` ghost-text path with Composer autocomplete; the prediction hides the placeholder while it shows. Sessions, quick tasks and projects get it through `ChatBody`; Manager Ave and new-session composers do not.
- Experimental flag key and resolved types are now derived from the validators in `shapes.ts`, so a new flag is declared once on the backend.

## Idle pause ignores visible but unattended tabs - 2026-10-09

- Cause: session 98 (carepulse-ts web) stayed awake overnight. Its last agent turn ended 2026-10-08 13:40 UTC, and every sweep credited `viewing` by its creator. The presence library drops a tab only when `document.hidden`, so a visible tab on an unattended screen held presence forever.
- New rule `isSandboxUserEngaged` (`@eva/shared`): a tab counts only when it is visible AND had input in the last `SANDBOX_ENGAGED_WINDOW_MS` (10 min). Input means pointer, key, wheel, scroll, touch, switching to the tab, or focus moving into a preview/editor iframe.
- Web: new `useUserEngaged` store. `SandboxPaneSlots` mounts the presence beacon and `SandboxAutoWake` only while it is true. Before, an open tab also auto-woke a paused sandbox straight away, with no visibility or input check.
- Preview proxy: one on-screen ping, served as `/__eva_preview_proxy/activity.js` and injected into every proxied document: preview, custom tabs, editor (code-server) and desktop (noVNC). It posts only while the page is visible with recent input. Browser traffic no longer counts by itself on any proxy; only the ping and non-browser API callers do (`countsAsActivity`). `SCRIPT_VERSION` stream-v28, so running proxies relaunch.
- Editor and desktop used to count raw traffic, so an open VS Code or VNC tab held its sandbox forever. The old "CSP blocks inline scripts" reason was stale (the proxy strips the CSP header); the external same-origin file also passes `'self'` CSPs such as code-server webviews.
- One rule, one source: `SANDBOX_ENGAGED_WINDOW_MS` and `SANDBOX_ENGAGEMENT_INPUT_EVENTS` in `@eva/shared` drive both the Eva app and the proxy ping.
- Effect: an untouched tab of any kind now holds the sandbox for up to 10 min plus the 60 min interaction grace.

## Many pull requests per session, quick task and project - 2026-10-07

- New `pullRequests` table: one row per PR, owned by a session (optionally a linked repo), a quick task (and run) or a project (and task/run). `_pullRequests/store.ts` is the only writer. Owners keep a summary (`prUrl`, `prState`, `prCount`) so list rows need no join; with one PR it reads exactly as before.
- One webhook handler, `githubWebhook:handlePullRequestEvent`, replaces `handleSessionPrEvent`, `handleProjectPrEvent` and `handlePrClosed`. It updates the row, attaches an unknown PR from its head branch (`eva/<kind>-<id>[-slug]`, same repo, not a fork), then lets the owner react.
- Rules now span every PR: a session archives, a quick task finishes and a project completes only once all its PRs are terminal. Archive and cancel close every live PR; undoing them reopens exactly those. Draft/ready and title sync stay on the primary PR. Create-vs-refresh checks for a live PR on the branch.
- The agent prompt tells agents to open their own PRs from `<chat branch>-<slug>` (was `eva/dup-<slug>`), so they link back to the chat.
